# plan-to-log-flows（E2E 仕様）

## 目的

「予定をログへ移動」は予定の削除とログの作成をまたぐ操作で、引き継ぎ漏れ・必須未入力での確定・未来日への誤表示のいずれもデータ欠損や誤削除に直結する。予定作成 → 移動導線 → ログ作成 → 予定消滅の往復と、バリデーション/未来日ゲートを実ブラウザで守る。

## 対象

- アプリ: service-front（http://localhost:9323）
- 画面 / URL: `/plans/new`、`/plans/{id}`（予定詳細）、`/plans`（一覧）、`/dives/new?fromPlanId=<id>`（引き継ぎ済みログ作成フォーム）、`/dives/{id}`（作成後のログ詳細）、`/dives`
- 関連仕様: `specs/024-plan-to-log/spec.md`（FR-001 当日以前の予定への導線、FR-002 未来日は導線なし、FR-004 / FR-005 予定日・ポイント名の引き継ぎ、FR-006 必須未入力ではログを作らない、FR-009 成功時のみ予定削除。quickstart S1〜S3）

## 前提

- 認証: ログイン済み（setup project の storageState）
- Cookie 同意: 同意済みプリセット（fixture 既定）
- データ: テスト内で予定を作成する（S1: `2024-06-30`「S1 予定→ログ移動の検証」、S3: `2024-06-30`「S3 必須未入力の検証」、S2: `2099-12-01`「S2 未来日ゲートの検証」）。S1 で作成したログはテスト内で削除、S2 / S3 の予定は `deletePlansByLocation` で削除して後始末する。ダイブ番号は `9000 + (Date.now() % 900)` で実行ごとに一意化
- その他: `test.describe.configure({ mode: 'serial' })` で直列実行（ダイブ番号の一意制約衝突を避けるため）。予定作成は `waitForHydration` 後に入力し、送信前に入力値が保持されていることを確認する

## シナリオ

| # | テスト名 | 検証内容 |
|---|---|---|
| 1 | S1: 当日以前の予定をログへ移動できる（引き継ぎ + 予定削除） | 予定を作成し「<ポイント名>の予定をログに記録する」リンクで `/dives/new?fromPlanId=` に遷移。ポイント名・潜水日（2024-06-30）が引き継がれている。ダイブ番号・最大水深 18・潜水時間 45 を入力して「作成する」→ `/dives/{id}` に遷移し見出しにポイント名が出る。`/plans` から元の予定が消えている。作成したログを削除して後始末。 |
| 2 | S3: 必須の潜水データ未入力では移動が確定しない | 予定を作成し移動導線から `/dives/new?fromPlanId=` へ。最大水深を空にして「作成する」を押しても URL が `/dives/new?fromPlanId=` のまま遷移しない。`/plans` に予定が残っていることを確認し削除する。 |
| 3 | S2: 未来日の予定には移動導線が出ない（一覧・詳細） | 未来日（2099-12-01）の予定を作成。詳細ページに「ログに記録する」リンクが無く、`/plans` 一覧でも当該予定の導線が無い（count 0）。一覧で axe 違反なし。予定を削除して後始末。 |

## 備考

- ダイブ番号は一意制約があるため直列実行し、失敗残骸と衝突しないよう実行ごとに一意な値を使う。S1 の後始末でログも削除して番号の残骸を残さない
- ログ詳細ではパンくずにも同名が出るため、ポイント名の確認は `heading` ロールに絞る
- 後始末ヘルパー `deletePlansByLocation` は「これからの予定」カード（「予定の詳細」リンク）と「終了済み」カード（カード全体が 1 リンク）の両方に対応し、送信の二重発火や過去実行の中断で同名予定が複数残っていても自己回復する
- S5（部分失敗）/ S6（重複防止）は Server Action の Vitest で担保し、ここでは扱わない
