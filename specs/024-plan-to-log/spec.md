# Feature Specification: ダイビング予定をログへ移動

**Feature Branch**: `024-plan-to-log`

**Created**: 2026-07-01

**Status**: Draft

**Input**: User description: "ダイビング予定をそのまま普通のログに移動できるようにしたい"

## 概要

ダイバーが登録済みの「ダイビング予定」（[004-top-dive-plans](../004-top-dive-plans/spec.md)）を、潜り終えたあとに手入力し直すことなく、そのまま「ダイビングログ」（[002-dive-log-crud](../002-dive-log-crud/spec.md)）へ**移動**できるようにする。予定に入力済みの内容（予定日・ポイント名・メモ）を新規ログに引き継ぎ、ログに必須の潜水データ（最大水深・潜水時間など）を補って保存すると、元の予定は削除される（＝予定からログへの「移動」）。

これにより「潜る前の計画（予定）」と「潜ったあとの記録（ログ）」が 1 本の流れでつながり、同じポイント名や日付を二度入力する手間がなくなる。

## Clarifications

### Session 2026-07-01

- Q: 予定をログに「移動」したあと、元の予定はどうなるべきか？ → A: 削除する（移動。ログ作成成功時に予定と持ち物リストを連動削除）
- Q: 未来日（予定日がまだ来ていない）の予定もログへ移動できるようにするか？ → A: 当日以降のみ許可（未来日の予定は移動導線を無効化。ログの潜水日は未来日を受け付けない）
- Q: ログの作成は成功したが、その直後の「予定の削除」に失敗した場合どう振る舞うべきか？ → A: ログを残し、削除失敗を通知する（ログを真実として保持し、予定は残るのでユーザーが手動削除できる）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 予定からログを起こして記録する (Priority: P1)

ダイバーとして、潜り終えた予定を選んで「ログに記録する」を押すと、予定の日付・ポイント名・メモが入力済みのログ作成フォームが開き、最大水深や潜水時間などの実績を足すだけでログを保存したい。保存すると元の予定は消え、ログ一覧に新しいログが並ぶ。

**Why this priority**: 本 feature の中核。これ単体で「予定を二度書きせずログにする」という価値がすべて成立する。

**Independent Test**: 過去日または当日の予定に対し「ログに記録」を実行 → 予定の内容が引き継がれたログ作成フォームが開く → 必須の潜水データを入力して保存 → ログ一覧に新規ログが表示され、元の予定が予定一覧から消えていることを確認できる。

**Acceptance Scenarios**:

1. **Given** 予定日が当日以前の予定が 1 件ある、**When** その予定で「ログに記録する」を選んだとき、**Then** システムは予定日・ポイント名・メモを引き継いだ新規ログ作成フォームを表示する
2. **Given** 引き継ぎ済みのログ作成フォームが開いている、**When** 最大水深・潜水時間（ログの必須項目）を入力して保存したとき、**Then** システムはログを作成し、元の予定を削除する
3. **Given** ログの作成に成功した、**When** 保存が完了したとき、**Then** システムは作成されたログの詳細ページへ遷移し、そのログを表示する
4. **Given** 引き継ぎ済みのフォームで必須の潜水データが未入力、**When** 保存しようとしたとき、**Then** システムは該当フィールドにエラーを表示し、ログを作成せず元の予定も削除しない
5. **Given** ログ作成フォームが引き継ぎ内容で開いている、**When** 保存せずに操作を中断（キャンセル / 離脱）したとき、**Then** システムはログを作成せず、元の予定もそのまま残す

---

### User Story 2 - まだ潜っていない未来の予定は移動できない (Priority: P2)

ダイバーとして、まだ日付が来ていない予定については「ログに記録する」導線が出ない（または無効）ことで、「これはまだ潜っていない予定だ」と直感的に分かるようにしたい。

**Why this priority**: ログの潜水日は未来日を受け付けないため、未来の予定を移動させると必ず保存エラーになる。導線段階で防ぐことで無駄な操作と混乱を避ける。US1 が動けば単独で追加できるガード。

**Independent Test**: 予定日が明日以降の予定では「ログに記録する」ボタンが表示されない（または押せない）こと、当日・過去日の予定では表示・操作できることを確認できる。

**Acceptance Scenarios**:

1. **Given** 予定日が翌日以降（未来）の予定、**When** 予定一覧または予定詳細を開いたとき、**Then** システムは「ログに記録する」導線を無効化または非表示にする
2. **Given** 予定日が当日または過去の予定、**When** 予定一覧または予定詳細を開いたとき、**Then** システムは「ログに記録する」導線を操作可能な状態で表示する

---

### Edge Cases

- **未来日の予定を移動しようとした場合** → 導線が無効化されているため通常は到達しない。仮に到達しても、`createDiveFromPlan` がサーバー側で `planned_on` を検証し、未来日は「未来の予定はログに移動できません。予定日を過ぎてから移動してください」で拒否する（FR-002）。ログは作成されず、予定も削除されない
- **引き継いだログの保存に失敗した場合**（ネットワーク / バリデーション / サーバーエラー）→ ログは作成せず、元の予定も削除しない（＝データが二重にも消失にもならない）
- **ログ作成は成功したが直後の予定削除に失敗した場合** → 作成したログはそのまま保持し（記録を真実とする）、予定の削除失敗をユーザーに通知する。予定は残るため、ユーザーは予定一覧から手動で削除できる（ログの取り消しは行わない）
- **移動対象の予定に持ち物リストが紐づいている場合** → 予定の削除に伴い持ち物リストも連動削除される（潜水後の記録に持ち物準備は不要なため）
- **予定のポイント名がポイントマスタに存在しない自由入力の場合** → ログ側もポイント名の自由入力として引き継ぐ（マスタ選択への自動変換は行わない）
- **予定のメモが長文の場合** → ログのメモ欄の上限に収まる範囲で引き継ぐ。上限を超える場合はユーザーが調整できるようフォーム上で編集可能とする
- **同じ予定を複数タブから同時に移動しようとした場合** → 先に成功した操作で予定が削除される。後続の操作は削除行数を確認し、0 行（並行操作で削除済み）の場合は `planDeleteFailed` として通知する（移動前の存在確認によりログの二重作成を防ぐ）
- **保存前にフォーム上で日付やポイント名を書き換えた場合** → ユーザーが編集した最終値でログを作成する（引き継ぎ値はあくまで初期値）

## Requirements *(mandatory)*

### Functional Requirements

#### 移動導線（予定一覧 / 予定詳細）

- **FR-001**: システムは、予定日が当日以前の予定に対して「ログに記録する」導線を予定一覧および予定詳細に表示しなければならない
- **FR-002**: システムは、予定日が翌日以降（未来）の予定に対しては「ログに記録する」導線を無効化または非表示にしなければならない（未来日判定は日本標準時の「今日」を基準とする）
- **FR-003**: システムは、「ログに記録する」導線を予定の所有者本人にのみ提供しなければならない

#### 引き継ぎ（プレフィル）

- **FR-004**: システムは、「ログに記録する」を実行したとき、対象予定の内容を初期値として引き継いだ新規ログ作成フォームを表示しなければならない
- **FR-005**: システムは、予定の**予定日をログの潜水日**、**ポイント名をログのポイント名**、**メモをログのメモ**として引き継がなければならない
- **FR-006**: システムは、ログにのみ存在する必須項目（最大水深・潜水時間）を空のままユーザーに入力させ、これらが未入力の場合はログを作成してはならない
- **FR-007**: システムは、引き継いだ初期値をユーザーがフォーム上で編集できるようにしなければならない（引き継ぎ値は確定値ではなく初期値）
- **FR-008**: システムは、予定のメモがログのメモ上限を超える場合でも、上限内に収めた形で引き継ぎ、ユーザーが調整できるようにしなければならない

#### 移動の確定（ログ作成 + 予定削除）

- **FR-009**: システムは、引き継いだフォームからのログ作成が成功したときに限り、元の予定を削除しなければならない
- **FR-010**: システムは、ログ作成が失敗したとき（バリデーション / サーバーエラー等）、ログを作成せず、かつ元の予定も削除してはならない
- **FR-011**: システムは、予定を削除したとき、その予定に紐づく持ち物リストも連動して削除しなければならない
- **FR-011a**: システムは、ログ作成に成功した後の予定削除に失敗したとき、作成済みのログは保持し（取り消さず）、予定削除に失敗した旨をユーザーに通知しなければならない。この場合、元の予定は残り、ユーザーが手動で削除できる状態を保つ
- **FR-012**: システムは、移動の完了後に作成されたログの詳細ページへ遷移し、そのログを確認できるようにしなければならない
- **FR-013**: システムは、移動によって作成されたログを、通常の新規作成ログと区別なく（同じデータ構造・同じ編集/削除操作で）扱えるようにしなければならない

#### データアクセス / 整合性

- **FR-014**: システムは、移動操作（ログ作成・予定削除）を認証ユーザー本人の予定・ログに限定しなければならない
- **FR-015**: システムは、対象予定が既に存在しない場合（他操作で削除済み等）、ログの重複作成を避け、その旨をユーザーに通知しなければならない

### Key Entities

- **dive_plans（既存 / 参照）**: 移動元のダイビング予定。`planned_on`（予定日）・`location`（ポイント名）・`notes`（メモ）を引き継ぎ元として使用し、移動成功時に削除される
- **plan_packing_items（既存 / 参照）**: 予定に紐づく持ち物リスト。予定削除に伴い連動削除される
- **dives（既存 / 参照）**: 移動先のダイビングログ。引き継いだ `dive_date` / `location` / `notes` に加え、必須の `max_depth_m` / `bottom_time_min` 等をユーザー入力で補完して新規作成される

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ユーザーは、予定日・ポイント名・メモを再入力することなく、当日以前の予定から新しいログを作成できる（引き継いだ 3 項目の再入力はゼロ）
- **SC-002**: 予定からログへの移動を、必須の潜水データ入力を含めて 1 分以内に完了できる
- **SC-003**: 移動が成功したとき、ログ一覧に新規ログが 1 件増え、予定一覧から対象予定が 1 件減る（作成と削除が 1 対 1 で整合する）
- **SC-004**: ログ作成に失敗したケースでは、ログが作成されず、かつ元の予定も残っている（二重作成・意図しない消失が発生しない）
- **SC-005**: 未来日の予定に対しては移動導線が提供されず、ユーザーが未来日の予定を誤ってログ化して保存エラーに遭遇することがない

## Assumptions

- 「移動」はコピーではなく**移動**であり、ログ作成成功時に元の予定を削除する（2026-07-01 ユーザー確認済み）
- 移動できるのは予定日が**当日以前**の予定のみとする。未来日の予定は導線を無効化する（2026-07-01 ユーザー確認済み。ログの潜水日が未来日を受け付けない仕様に整合）
- 潜水日の初期値には予定の予定日をそのまま用いる（当日以前に限定されるため、ログの潜水日制約を満たす）
- ポイント名は予定の自由入力テキストをログのポイント名（自由入力）として引き継ぎ、ポイントマスタ（011）への自動マッチングは行わない
- 持ち物リストは潜水前の準備用データであり、ログには引き継がない（予定削除に伴う連動削除で消える）
- 移動導線の設置箇所は予定一覧および予定詳細を想定する。具体的な UI 配置は plan / screens で詳細化する
- 引き継ぎ以外のログの入力項目（コンディション・装備・ガス等の任意項目）は通常のログ作成と同じく任意入力とする
