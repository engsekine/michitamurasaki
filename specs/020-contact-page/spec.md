# Feature Specification: お問い合わせページ

**Feature Branch**: `020-contact-page`

**Created**: 2026-06-29

**Status**: Draft

**Input**: User description: "別のワークツリーでお問い合わせページ追加実装をして 020番"

## Clarifications

### Session 2026-06-29

- Q: お問い合わせ内容の送信先・保存方法は? → A: **DB に保存し、既存の管理パネル(015)から運営者が閲覧**する（メール通知は本機能の範囲外）
- Q: お問い合わせページのアクセス範囲は? → A: **公開（ログイン不要）**。未ログインでも送信できるよう、氏名・メールアドレスの入力欄を持つ
- Q: 問い合わせ本文の最大文字数は? → A: **1,000 文字**（超過時は送信を拒否）
- Q: 問い合わせ種別の選択肢は? → A: **ご質問 / 不具合報告 / ご要望 / その他**（4 種・必須・単一選択）
- Q: 多重送信・スパム対策の方式は? → A: **連打防止（送信中ボタン無効化＋同一内容の即時重複拒否）＋ 送信レート制限 ＋ ハニーポット**。外部 CAPTCHA は導入しない
- Q: 収集した個人情報（氏名・メール）の保持方針は? → A: **無期限保持**し、運営者が管理パネルから**手動で削除**できる（自動削除はしない）

### Session 2026-06-29（スコープ拡張: 確認画面・サンクスページ・メール通知）

- Q: 送信フローに確認画面・完了画面を設けるか? → A: **入力 → 確認画面 → 送信 → 完了（サンクス）画面 `/contact/complete`** の 3 段にする
- Q: メール通知の種類は? → A: **運営者への通知メール ＋ 送信者への自動返信メール**の 2 通
- Q: メール送信基盤は? → A: **Resend（HTTP API）**。Vercel のサーバーレス上で生 SMTP より安定する。API キー（`RESEND_API_KEY`）を env に置く（当初 SMTP/nodemailer 案から変更）
- Q: 通知メール送信に失敗したときの扱いは? → A: **厳密（通知必須）**。保存済みの行を取り消し、確認画面で再送をうながす

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 訪問者がお問い合わせを送信する (Priority: P1)

サービスの訪問者（ログインの有無を問わない）として、お問い合わせページから氏名・メールアドレス・問い合わせ種別・本文を入力し、**確認画面で内容を確認してから送信**し、運営者に内容を届けたい。送信後は**専用の完了（サンクス）画面**で受付できたことが分かることを期待する。

**Why this priority**: お問い合わせの「送信」が成立しなければページの存在価値がない。本機能の中心であり、これ単体で「訪問者が運営に連絡できる」という価値を提供する MVP。確認画面は誤送信を防ぎ、完了画面は受付の明確なフィードバックを与える。

**Independent Test**: `/contact` を未ログイン状態で開き、必須項目を入力 → 確認画面で内容を確認 → 送信 → 完了（サンクス）画面に遷移し、内容が記録されることを確認すれば単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 未ログインの訪問者が `/contact` を開いている、**When** 氏名・メールアドレス・問い合わせ種別・本文をすべて正しく入力して「確認画面へ進む」を押す、**Then** システムは入力内容（種別は表示ラベル）を確認画面に表示する
2. **Given** 訪問者が確認画面で内容を確認している、**When** 「送信する」を押す、**Then** システムは問い合わせを受け付けて記録し、完了（サンクス）画面 `/contact/complete` へ遷移する
3. **Given** 訪問者が確認画面を表示している、**When** 「入力内容を修正する」を押す、**Then** システムは入力画面に戻し、入力済みの値を保持する
4. **Given** 訪問者がフォームを開いている、**When** 必須項目を空のまま「確認画面へ進む」を押す、**Then** システムは確認画面に進まず、どの項目が必要かをエラーで示す
5. **Given** 訪問者がメールアドレス欄に形式不正な値を入力した、**When** 「確認画面へ進む」を押す、**Then** システムはエラーを表示し確認画面に進まない
6. **Given** 訪問者が本文に許容文字数を超える長文を入力した、**When** 「確認画面へ進む」を押す、**Then** システムはエラーを表示し確認画面に進まない

---

### User Story 2 - 運営者が届いたお問い合わせを確認する (Priority: P2)

運営者（管理パネルの利用者）として、届いたお問い合わせの一覧と詳細（氏名・メールアドレス・種別・本文・受付日時）を管理パネルから閲覧し、対応の要否を判断したい。

**Why this priority**: 送信（US1）が成立した後に、運営側が内容を受け取れて初めて業務として完結する。送信機能に次いで重要なため P2。

**Independent Test**: 既存の管理パネルにお問い合わせ一覧の導線が現れ、US1 で送信した問い合わせが新しい順に一覧・詳細で確認できることを確認すれば単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 1 件以上の問い合わせが記録されている、**When** 運営者が管理パネルのお問い合わせ一覧を開く、**Then** システムは受付日時の新しい順に問い合わせを一覧表示する
2. **Given** 運営者が一覧から 1 件を選ぶ、**When** 詳細を開く、**Then** システムは氏名・メールアドレス・種別・本文・受付日時を表示する
3. **Given** 問い合わせが 0 件、**When** 運営者が一覧を開く、**Then** システムは「お問い合わせはありません」の空状態を表示する
4. **Given** 管理パネルにアクセス権のない一般利用者、**When** お問い合わせ一覧の URL に直接アクセスする、**Then** システムは閲覧を拒否する
5. **Given** 運営者が対応済み等で不要になった問い合わせを選んでいる、**When** 削除を実行する、**Then** システムはその問い合わせを削除し、一覧から除外する

---

### User Story 3 - ログイン中ユーザーは入力が補完される (Priority: P3)

ログイン中のユーザーとして、お問い合わせフォームを開いたときに自分の氏名・メールアドレスがあらかじめ入っていることで、入力の手間を減らしたい。

**Why this priority**: 公開フォーム（US1）が成立していれば送信は可能であり、補完は利便性向上の付加価値のため P3。

**Independent Test**: ログイン状態で `/contact` を開き、氏名・メールアドレスが自分のアカウント情報で初期表示されること、編集して送信できることを確認すれば単独で検証できる。

**Acceptance Scenarios**:

1. **Given** ログイン中のユーザーが `/contact` を開いた、**When** フォームが表示される、**Then** システムは氏名・メールアドレスをアカウント情報で初期表示する
2. **Given** 初期表示された氏名・メールアドレス、**When** ユーザーがそれを編集して送信する、**Then** システムは編集後の値で問い合わせを記録する

---

### Edge Cases

- 必須項目（氏名・メールアドレス・問い合わせ種別・本文）が未入力 → エラーを表示して送信を拒否する
- メールアドレスが形式不正 → エラーを表示して送信を拒否する
- 本文が 1,000 文字を超過 / 0 文字 → エラーを表示して送信を拒否する
- 同一内容を短時間に連続送信（多重送信・スパム）→ 送信を抑制し、重複登録を防ぐ
- レート制限を超える送信 → 送信を拒否し、時間をおいて再送するようエラーで伝える
- ハニーポット項目に値が入った送信（bot 想定）→ 完了画面へ遷移しても問い合わせは記録しない
- 送信処理が失敗した（保存に失敗）→ 完了画面へ遷移せず、確認画面で再送をうながすエラーを表示する
- 確認画面から修正に戻る → 入力済みの値を保持したまま入力画面に戻す
- 完了画面に直接アクセス（送信を経ずに `/contact/complete` を開く）→ 静的な受付完了表示として閲覧でき、エラーにはしない
- 保存は成功したが通知メール送信に失敗 → 保存済みの行を取り消し、確認画面で再送をうながす（厳密通知 / FR-023）。取り消しにより再送時に重複ガードへ当たらない
- メール送信基盤の設定（`RESEND_API_KEY` / 差出人 / 宛先）が未構成 → 送信は失敗扱いとし、完了画面へ遷移させない
- 未ログイン訪問者の送信 → ログインを要求せずに受け付ける（氏名・メールは入力値を使用）
- 管理パネルで問い合わせ詳細の本文にスクリプト等が含まれる → 表示時に無害化し、運営者の画面で実行されない

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは公開ページ `/contact` を提供し、ログインの有無に関わらずアクセスできなければならない
- **FR-002**: お問い合わせフォームは「氏名」「メールアドレス」「問い合わせ種別」「本文」の入力を受け付けなければならない
- **FR-003**: システムは「氏名」「メールアドレス」「問い合わせ種別」「本文」を必須として検証し、不足時は送信を拒否してエラーを表示しなければならない
- **FR-004**: システムはメールアドレスの形式を検証し、不正な場合は送信を拒否しなければならない
- **FR-005**: システムは本文の文字数上限を **1,000 文字**とし、上限超過時は送信を拒否しなければならない
- **FR-006**: 問い合わせ種別は「ご質問 / 不具合報告 / ご要望 / その他」の 4 択から 1 つを選ぶ形式とし、選択肢以外の値を受け付けてはならない
- **FR-007**: 送信が成立した場合、システムは問い合わせ内容（氏名・メールアドレス・種別・本文・受付日時）を永続化しなければならない
- **FR-008**: 送信が成立した（＝問い合わせの保存と通知メール送信の双方が成功した）場合、システムは専用の完了（サンクス）画面 `/contact/complete` へ遷移し、受付できたことを利用者に明示しなければならない
- **FR-009**: 送信処理が失敗した（保存失敗、または通知メール送信失敗）場合、システムは完了画面へ遷移させず、確認画面にとどめて再送をうながすエラーを表示しなければならない
- **FR-010**: システムは保存された問い合わせを、権限を持つ運営者が管理パネルから一覧・詳細で閲覧できるようにしなければならない
- **FR-011**: 管理パネルの問い合わせ一覧は受付日時の新しい順に表示しなければならない
- **FR-012**: システムは管理パネルへのアクセス権を持たない利用者に対し、問い合わせの閲覧を拒否しなければならない
- **FR-013**: ログイン中のユーザーがフォームを開いた場合、システムは氏名・メールアドレスをアカウント情報で初期表示し、ユーザーは編集できなければならない
- **FR-014**: システムは多重送信・スパム的な連続送信を、次の手段で抑制し意図しない重複登録を防がなければならない: (a) 送信処理中の送信操作の無効化、(b) 同一内容の即時重複送信の拒否、(c) 一定時間あたりの送信数のレート制限、(d) ハニーポット項目による bot 送信の抑制。外部 CAPTCHA は本機能では導入しない
- **FR-015**: システムは問い合わせ本文・氏名等の表示時に無害化し、運営者・利用者の画面で入力由来のスクリプトが実行されないようにしなければならない
- **FR-016**: お問い合わせページへの導線（フッター等）を設け、利用者がページに到達できるようにしなければならない
- **FR-017**: システムは保存した問い合わせを無期限に保持し、自動削除してはならない
- **FR-018**: 権限を持つ運営者は、管理パネルから問い合わせを手動で削除できなければならない
- **FR-019**: システムは送信前に確認画面を表示し、入力内容（種別は表示ラベル）を確認させなければならない。確認画面からは「送信」と「入力内容の修正（入力値を保持して入力画面へ戻る）」を選べなければならない
- **FR-020**: システムは送信完了後に公開ページ `/contact/complete`（完了・サンクス画面）を表示し、受付の旨と次の導線（ホーム等）を提示しなければならない
- **FR-021**: 送信成立時、システムは運営者の通知先アドレスへ問い合わせ内容（氏名・メール・種別・本文）を含む通知メールを送らなければならない。返信先（Reply-To）は送信者のメールアドレスとする
- **FR-022**: 送信成立時、システムは送信者のメールアドレスへ受付確認の自動返信メールを送らなければならない
- **FR-023**: 通知メール（FR-021 / FR-022）のいずれかが送信に失敗した場合、システムは保存済みの問い合わせを取り消し（再送時の重複登録・重複ガード抵触を防ぐ）、利用者に失敗を返さなければならない

### Key Entities *(include if feature involves data)*

- **お問い合わせ (Inquiry)**: 訪問者が送信した 1 件の問い合わせ。属性: 氏名、メールアドレス、問い合わせ種別、本文（1〜1,000 文字）、受付日時、（任意）送信者のユーザー識別子（ログイン中に送信された場合のみ）。運営者が閲覧する対象。
- **問い合わせ種別 (Inquiry Category)**: 問い合わせを分類する固定の選択肢「ご質問 / 不具合報告 / ご要望 / その他」。問い合わせは必ず 1 つの種別に属する。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 訪問者は `/contact` で必須項目の入力から送信完了まで 2 分以内に完了できる
- **SC-002**: 必須項目の不足・メール形式不正・本文超過のいずれの不備でも、送信前に該当箇所のエラーが利用者に伝わり、不正な内容が保存される割合が 0% である
- **SC-003**: 送信に成功した問い合わせは 100% が管理パネルの一覧で確認でき、欠落・重複が発生しない
- **SC-004**: 管理パネルのアクセス権を持たない利用者からの問い合わせ閲覧は 100% 拒否される
- **SC-005**: ログイン中ユーザーの 90% 以上が、氏名・メールアドレスを再入力せずに送信を完了できる

## Assumptions

- お問い合わせは「DB 保存 + 管理パネルでの閲覧」に加え、**メール通知も行う**（スコープ拡張で追加）。運営者への通知メールと、送信者への自動返信メールの 2 通を送る。送信基盤は **Resend（HTTP API）**。プッシュ通知は範囲外。
- メール送信は **厳密（通知必須）**。保存に成功しても通知メール送信に失敗した場合は「受付完了」とせず、保存した行を取り消して（`discard_recent_inquiry`）失敗を返す。これにより再送時に重複ガードへ当たらない。
- ページは公開（ログイン不要）とし、未ログイン訪問者のために氏名・メールアドレスの入力欄を持つ（クラリフィケーションで確定）。
- 管理パネルでの閲覧は既存の管理機能（spec 015-admin-panel）の権限・画面構成に準拠し、新規の問い合わせ閲覧画面をその枠組みに追加する。
- 問い合わせ種別は「ご質問 / 不具合報告 / ご要望 / その他」の 4 択で確定（クラリフィケーションで確定）。
- 既存の Cookie 同意（017）・利用規約（018）等の公開ページと同じレイアウト（Header / Footer）方針に従う。
- 本機能では運営者が問い合わせに「返信」する機能（ステータス管理・対応履歴）は範囲外とし、閲覧と手動削除を対象とする。
- 収集した個人情報を含む問い合わせは無期限に保持し、運営者が管理パネルから手動削除できる（自動削除はしない・クラリフィケーションで確定）。
- スパム対策は連打防止・同一内容の即時重複拒否・レート制限・ハニーポットで行い、外部 CAPTCHA は導入しない（クラリフィケーションで確定）。レート制限の具体的な閾値・計測単位は計画フェーズで決定する。
