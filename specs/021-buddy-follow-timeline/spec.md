# Feature Specification: バディ・フォロー・タイムライン（ソーシャル機能）

**Feature Branch**: `021-buddy-follow-timeline`

**Created**: 2026-06-29

**Status**: Draft

**Input**: User description: "機能: バディ／同行者ログ。価値: 「誰と潜ったか」は紙ログの定番。SNS 的なつながりの起点にもなる。既存との接続: dive_log_buddies 中間テーブル（dives×users/フリーテキスト）。検索(013)にも追加。規模感: 中 / フォロー機能を作成 / フォローした相手のログを見られる / フォロー解除も可能 / ログの公開・非公開機能 / TOP ページにタイムライン表示"

## 概要

ダイビングログに「誰と潜ったか（バディ／同行者）」を記録し、それを起点にユーザー同士がフォローでつながり、公開されたログをタイムラインで楽しめるようにする**ソーシャルレイヤー**を追加する。既存のダイブログ（002）に用意済みの公開用カラム（`is_public` / `public_slug`）と、フリーテキストのバディ欄（`buddy_name`）を土台として、登録ユーザーのバディタグ付け・フォロー・公開範囲制御・タイムラインを実現する。

> 用語: 本仕様では「バディ」と「同行者」を同義として扱う。

## Clarifications

### Session 2026-07-01

- **公開ログの閲覧経路の統合（FR-010/011 改定）**: 匿名共有ページ `/(public)/shared/dives/[slug]` を廃止し、公開ログの閲覧はログイン済みユーザー向けの `/dives/[id]` に一本化する。共有リンクは `{SITE_URL}/dives/[id]`（dive id ベース）。未ログイン（匿名）からは閲覧できない。`public_slug` を使った匿名 RPC（`get_public_dive`）は撤去する。
- **他人の公開ログの閲覧範囲（FR-010 改定）**: 他ユーザーの公開ログ詳細は写真・同行バディを含む全項目を表示する。ただし編集・削除・公開設定・PDF 出力は作成者本人のみ（`canManage`）。
- **編集・削除の権限（FR-025 追加）**: ダイブログの編集・削除は作成者本人のみ可能。他人の公開ログを閲覧できても編集・削除はできない（UI 非表示 + Server Action の owner チェック + RLS の三重防御）。

### Session 2026-06-29

- **公開ログの閲覧範囲（FR-010）**: 公開ログは「ログイン済みユーザーが共有リンク（`/dives/[id]`）から閲覧可」かつ「フォロワーのタイムライン・公開ログ一覧に表示」とする（Session 2026-07-01 で匿名閲覧を廃止）。
- **フォローモデル（FR-012）**: 承認不要の一方向フォロー（Twitter 型）。何が見えるかは各ログの公開設定で制御する。
- **バディタグ付けの合意（FR-024）**: 合意・通知なしでタグ付け可。ただしタグ付けされた本人は、自分へのタグをいつでも自分で除去できる。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 同行したバディをログに記録・表示する (Priority: P1)

ダイバーがダイブログを作成・編集するとき、その日一緒に潜った同行者（バディ）を記録できる。バディはこのアプリの登録ユーザー、またはアプリ未登録の人のフリーテキスト名で指定でき、1 本のログに複数人を記録できる。ログ詳細を見ると「誰と潜ったか」が一覧で分かり、登録ユーザーのバディはその人のプロフィールへ辿れる。

**Why this priority**: 「誰と潜ったか」は紙ログの定番項目であり、本機能の中核価値。フォローやタイムラインが無くても、バディ記録だけで単独の価値（記録・振り返り）を提供できる MVP スライス。

**Independent Test**: ダイブログ編集画面でバディ（登録ユーザー＋フリーテキスト）を追加し、保存後にログ詳細でバディ一覧が表示され、登録ユーザーのバディからプロフィールへ遷移できることを確認するだけでテスト可能。

**Acceptance Scenarios**:

1. **Given** ログ編集画面を開いている, **When** 登録ユーザーをバディとして選び保存する, **Then** ログ詳細にそのバディが表示され、プロフィールへのリンクが張られる
2. **Given** ログ編集画面を開いている, **When** 未登録の人の名前をフリーテキストで入力し保存する, **Then** ログ詳細にその名前がバディとして表示される
3. **Given** 1 本のログに複数バディを登録している, **When** ログ詳細を表示する, **Then** すべてのバディが一覧表示される
4. **Given** 他人のログを閲覧している, **When** バディの追加・削除を試みる, **Then** 操作できない（所有者のみ編集可能）

---

### User Story 2 - ログの公開・非公開を切り替える (Priority: P2)

ダイバーは各ダイブログを「公開」か「非公開」かを自分で選べる。新規ログは既定で非公開。公開にしたログだけが、他ユーザー（フォロワー等）やタイムラインから見えるようになる。公開を取りやめれば、即座に他者から見えなくなる。

**Why this priority**: 公開範囲の制御は、フォロー・タイムラインなどあらゆる他者閲覧機能の前提となる安全装置。これ単体でも「特定のログだけを共有リンク（`/dives/[id]`）でログインユーザーに見せる」という価値を提供できる。

**Independent Test**: 1 本のログを公開に切り替え、別アカウントで共有リンク（`/dives/[id]`）からそのログだけが閲覧でき（編集・削除ボタンは出ない）、非公開ログは閲覧できないことを確認できる。

**Acceptance Scenarios**:

1. **Given** 非公開のログを所有している, **When** 公開に切り替える, **Then** そのログが他者から閲覧可能になる
2. **Given** 公開中のログを所有している, **When** 非公開に戻す, **Then** 他者（フォロワー・タイムライン・共有リンク）から即座に閲覧できなくなる
3. **Given** 新規ログを作成する, **When** 公開設定を変更せず保存する, **Then** 既定で非公開として保存される
4. **Given** 他ユーザーの非公開ログ, **When** その URL に直接アクセスする, **Then** 閲覧できない
5. **Given** 他ユーザーの公開ログ, **When** `/dives/[id]` を閲覧する, **Then** 全項目を閲覧できるが編集・削除・公開設定・PDF 出力の操作は表示されない
6. **Given** 未ログイン, **When** 公開ログの `/dives/[id]` にアクセスする, **Then** ログインへ誘導され閲覧できない

---

### User Story 3 - ユーザーをフォロー／解除し、相手の公開ログを見る (Priority: P2)

ダイバーは気になる他ダイバーをフォローでき、フォロー中の相手が公開しているログを一覧で閲覧できる。フォローはいつでも自分の操作で解除できる。フォロー／フォロワーの一覧と件数を確認できる。

**Why this priority**: SNS 的なつながりの起点であり、ユーザー要望の中心。公開範囲制御（US2）の上に成立する。

**Independent Test**: アカウント A から B をフォローし、B の公開ログ一覧が A から見えること、フォロー解除すると見え方・件数が更新されることを確認できる。

**Acceptance Scenarios**:

1. **Given** 別ユーザーのプロフィールを見ている, **When** フォローする, **Then** フォロー中になり、相手のフォロワー数と自分のフォロー数が増える
2. **Given** あるユーザーをフォロー中, **When** フォロー解除する, **Then** フォロー関係が解消され、件数が減る
3. **Given** B をフォロー中, **When** B の公開ログ一覧を開く, **Then** B の公開ログのみが表示され、B の非公開ログは含まれない
4. **Given** 自分自身のプロフィール, **When** フォロー操作を試みる, **Then** 自分自身はフォローできない

---

### User Story 4 - TOP ページのタイムラインで公開ログを見る (Priority: P3)

ログイン後の TOP ページに、フォロー中ユーザーの公開ログを新しい順に並べたタイムラインが表示される。各項目から該当ログの詳細へ遷移できる。フォローが居ない／対象の公開ログが無い場合は空状態が表示される。

**Why this priority**: つながりの「楽しさ」を可視化する体験だが、バディ記録・公開・フォローが揃って初めて意味を持つ集約ビュー。

**Independent Test**: 複数フォロー先に公開ログがある状態で TOP を開き、新しい順に並ぶこと・詳細へ遷移できること・非公開が混ざらないことを確認できる。

**Acceptance Scenarios**:

1. **Given** フォロー中ユーザーに複数の公開ログがある, **When** TOP を開く, **Then** それらが新しい順にタイムライン表示される
2. **Given** タイムラインの項目, **When** 項目を選ぶ, **Then** 対応するログ詳細へ遷移する
3. **Given** 誰もフォローしていない, **When** TOP を開く, **Then** フォローを促す空状態が表示される
4. **Given** フォロー中ユーザーが公開ログを持たない, **When** TOP を開く, **Then** 空状態が表示され、非公開ログは決して現れない

---

### User Story 5 - 検索でバディから絞り込む（013 拡張） (Priority: P3)

ダイブ検索（013）に「バディ」での絞り込み条件を追加し、特定の同行者と潜ったログを探せる。

**Why this priority**: バディ記録（US1）が蓄積された後に効く付加的な発見手段。既存検索への小さな拡張。

**Independent Test**: 特定のバディを記録した複数ログを用意し、検索でそのバディを条件に指定して、該当ログだけが返ることを確認できる。

**Acceptance Scenarios**:

1. **Given** あるバディを含むログが複数ある, **When** 検索でそのバディを条件に指定する, **Then** 該当ログのみが結果に表示される
2. **Given** 検索を実行する, **When** 結果を表示する, **Then** 閲覧権限のあるログ（自分のログ＋閲覧可能な公開ログ）のみが返る

---

### Edge Cases

- バディとしてタグ付けした登録ユーザーが**退会**した場合、そのバディ表示はどうなるか（リンク切れを避けるためフリーテキスト名へフォールバック、またはタグ自体を削除）。
- フォロー中の相手が**全ログを非公開**にした場合、タイムライン・公開ログ一覧は空になる（非公開は決して露出しない）。
- 公開ログを**非公開に戻した**とき、既に共有された公開リンク（`public_slug`）が無効化される。
- **自己フォロー・重複フォロー**は成立しない。
- バディに**自分自身**を登録しようとした場合の扱い（不可、または無視）。
- 退会ユーザーに紐づく**フォロー関係・バディタグ**のクリーンアップ。
- フォロー数が非常に多いユーザーのタイムライン表示性能（ページング／件数上限）。
- 同一人物を「登録ユーザー」と「フリーテキスト」で二重にバディ登録した場合は、システム的な突合は行わず両方表示する（フリーテキストは本人特定不可のため。重複表示は許容する）。

## Requirements *(mandatory)*

### Functional Requirements

#### バディ（同行者）記録

- **FR-001**: ダイブログの作成・編集時に、同行したバディを 0 人以上記録できる。
- **FR-002**: バディは「アプリの登録ユーザー」または「フリーテキスト名（未登録者）」のいずれかで指定できる。
- **FR-003**: 1 本のダイブログに複数のバディを記録でき、各バディは独立した 1 件として管理される（繰り返しカラムを使わない）。
- **FR-004**: ダイブログ詳細でバディ一覧を表示する。登録ユーザーのバディは表示名（nickname）で表示し、その人のプロフィールへ遷移できる。
- **FR-005**: バディの追加・編集・削除は、そのログの所有者のみが行える。
- **FR-006**: 既存のフリーテキストのバディ情報（`buddy_name`）と整合する形で移行・併存できる。

#### 公開・非公開（Visibility）

- **FR-007**: 各ダイブログは「公開」「非公開」の状態を持ち、所有者が切り替えられる。
- **FR-008**: 新規作成されるダイブログの既定は「非公開」である。
- **FR-009**: 非公開ログは、所有者以外（フォロワーを含む）から一切閲覧できない。
- **FR-010**: 公開ログは、(a) ログイン済みユーザーが共有リンク（`/dives/[id]`）から閲覧でき（写真・同行バディを含む全項目。ただし編集・削除・公開設定・PDF 出力は作成者本人のみ）、かつ (b) フォロワーのタイムライン・公開ログ一覧にも表示される。未ログイン（匿名）からは閲覧できない。
- **FR-011**: 公開ログの共有リンクは dive id ベースの `{SITE_URL}/dives/[id]` とする。非公開化すると当該 URL からの閲覧も即座に無効化される（RLS が `is_public=false` を弾く）。匿名共有用の `public_slug` / `get_public_dive` RPC は廃止する。
- **FR-025**: ダイブログの編集・削除は作成者本人のみが行える。他人の公開ログを閲覧できても編集・削除はできない（UI 非表示 + Server Action の owner チェック + RLS の三重防御）。

#### フォロー

- **FR-012**: ユーザーは他のユーザーを**承認不要で一方向にフォロー**できる（フォローは即成立し、相手の承認は不要）。何が見えるかは各ログの公開設定（FR-007〜FR-010）で制御される。
- **FR-013**: ユーザーは自分がフォローしている相手を、いつでも自分の操作でフォロー解除できる。
- **FR-014**: ユーザーは自分自身をフォローできず、同じ相手を重複してフォローできない。
- **FR-015**: フォロー中の相手の「公開ログ」を一覧で閲覧できる（非公開ログは含めない）。
- **FR-016**: 自分のフォロー一覧・フォロワー一覧と、それぞれの件数を表示できる。
- **FR-016a**: フォロー関係（user_follows）は認証ユーザー全体に読み取り公開（`using (true)`）であり、他ユーザーのフォロー/フォロワー一覧も閲覧できる（Twitter 型の設計判断）。

#### タイムライン（TOP）

- **FR-017**: TOP ページに、フォロー中ユーザーの公開ログを新しい順に並べたタイムラインを表示する。
- **FR-018**: タイムラインの各項目から、対応するダイブログ詳細へ遷移できる。
- **FR-019**: タイムラインには非公開ログを一切含めない。
- **FR-020**: フォローが 0 件、または対象の公開ログが無い場合は、行動を促す空状態を表示する。
- **FR-021**: タイムラインは件数上限またはページングを備え、フォロー数が多くても表示できる。

#### 検索（013 拡張）

- **FR-022**: ダイブ検索（013）に、バディ（登録ユーザー／フリーテキスト名）による絞り込み条件を追加する。
- **FR-023**: 検索対象は本人ログのみ（`fetchDiveListPage` が `user_id=self` を固定。公開ログは検索対象外）。

#### バディタグ付けのプライバシー

- **FR-024**: 登録ユーザーは、事前の合意・通知なしにバディとしてタグ付けでき、そのタグはログの公開範囲（FR-010）に従って表示される。
- **FR-024a**: バディとしてタグ付けされた本人は、自分に対して付けられたタグを、他人のログであってもいつでも自分で除去できる。
- **FR-024b**: 自分へのタグを除去した相手から再度同一ログにタグ付けされないよう、本人の除去操作が優先される（除去後の再タグ付けはブロックされる）。

#### 横断（セキュリティ）

- **FR-025**: すべてのデータアクセスは行レベルセキュリティで保護し、非公開ログ・他者のフォロー関係などの不正閲覧・改変を防ぐ（constitution「Security & RLS by Default」準拠）。

### Key Entities *(include if feature involves data)*

- **Dive Log（既存 `dives`）**: ダイビング 1 本のログ。本機能では `is_public`（公開フラグ）・`public_slug`（公開識別子）を活性化し、バディとの関連を持つ。所有者は `user_id`。
- **Dive Buddy（新規・中間テーブル `dive_log_buddies`）**: ダイブログと同行者の関連。1 件ごとに「登録ユーザーへの参照」または「フリーテキスト名」のいずれかを保持する（dives × users / フリーテキストの多対多を正規化）。
- **Follow（新規・フォロー関係）**: 「フォローする人」→「フォローされる人」の自己参照的な多対多関係。同一ペアは一意、自己フォロー不可。
- **User（既存 `users` / `user_details`）**: 表示名は `nickname`。バディタグ・フォローの参照先であり、退会時は関連（バディタグ・フォロー）のクリーンアップ対象。
- **Timeline（導出ビュー）**: 実テーブルではなく、フォロー関係と公開ログから導出される、フォロー中ユーザーの公開ログの時系列集約。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ユーザーはログ編集画面で、登録ユーザー／フリーテキストのバディを 30 秒以内に追加・保存できる。
- **SC-002**: 非公開ログが所有者以外に表示される事故が 0 件（全閲覧経路＝直接 URL・一覧・タイムライン・検索・共有リンクで権限テストを通過）。
- **SC-003**: フォロー／フォロー解除の操作結果（関係・件数）が 3 秒以内に画面へ反映され、フォロー数とフォロワー数が常に整合する。
- **SC-004**: TOP タイムラインは最新の公開ログ 20 件を 2 秒以内に表示する。
- **SC-005**: 公開ログを非公開に戻した後、他者からの閲覧（一覧・タイムライン・共有リンク）が 5 秒以内にすべて遮断される。
- **SC-006**: バディ条件を指定したダイブ検索が、該当ログを 1 秒以内に返す。
- **SC-007**: ログ詳細で「誰と潜ったか」を、登録ユーザー・フリーテキストの区別なく 1 画面で把握できる（ユーザーテストで主要タスク完了率 90% 以上）。

## Assumptions

- 既存ダイブログ（002）の Phase 2 用カラム `dives.is_public` / `dives.public_slug` を本機能で活性化して利用する。
- 既存のフリーテキストのバディ欄 `dives.buddy_name` は、新規の中間テーブル `dive_log_buddies` による記録と併存／移行する。
- バディ・フォロー・タイムラインの利用者は**認証済みユーザー**で、既存の認証基盤（001 / Google ログイン 016）を再利用する。
- ユーザーの表示名には `user_details.nickname` を用いる。
- タイムライン・公開ログ一覧・検索結果の既定ソートは「新しい順（ダイブ日時／作成日時の降順）」。
- アクセス制御は Supabase の RLS で担保し、アプリ側バリデーションだけに依存しない（constitution IV）。
- 退会（ユーザー削除）時は、外部キーの連鎖削除によりバディタグ・フォロー関係も整理される。
- 本機能は Web（既存 service-front）を対象とし、管理側（admin-front）の新規 UI は対象外。
- 通知（フォローされた／タグ付けされた等のプッシュ・メール通知）は本機能のスコープ外（将来拡張）。
- 公開ログの閲覧はログイン済みユーザー向けの `/dives/[id]` に統合する（匿名共有ページは廃止）。他人の公開ログでも写真・同行バディを含む全項目を表示するが、編集・削除・公開設定・PDF 出力は作成者本人のみに限定する。

## 実装メモ（現状の制約）

- **ユーザー検索・フォロー導線を追加済み**（`search_users_by_handle` 関数 + `/users/search` ページ + `UserSearchBar`）。ユーザー ID（handle）部分一致で相手を探し（当初の nickname 検索から変更）、検索結果・プロフィール・フォロー一覧から `FollowButton` でフォローできる。検索結果・フォロー一覧（`FollowList`）の各行は nickname に加えて `@ユーザーID` を併記する。加えて、アカウントメニュー（`AuthNav`）に「マイプロフィール」「ユーザーを探す」導線、TOP タイムライン各項目に投稿者プロフィールへのリンクを追加。
- **登録ユーザーのバディ「追加」UI（FR-002）は未提供**。現状は ① フォームでフリーテキスト名のバディ追加、② 既存の登録ユーザーバディの表示（プロフィールリンク）・削除、までを実装。上記ユーザー検索をバディ登録ピッカーに再利用する新規タグ付け UI は引き続き将来対応。
- **バディ検索（FR-022）**: UI では「バディ名（フリーテキスト部分一致）」のみ提供。登録ユーザー指定（`?buddy=<userId>`）は URL パラメータでのみ機能する（検索 UI のユーザーピッカーは上記と同じく将来対応）。
- 退会フォールバック・公開ログの RLS 全経路遮断・フォロー系クエリの検証は Supabase 実 DB での結合テストで担保する（quickstart 参照）。
