# Feature Specification: CI/CD 整備（GitHub Actions）

**Feature Branch**: `005-github-actions-ci`

**Created**: 2026-06-11

**Status**: Draft

**Input**: User description: "CI/CD周りの整備 github actionsで実行したい"

## Clarifications

- Session 2026-07-17: **CI / Full Test を手動実行（workflow_dispatch）へ移行**。PR・push 連動の自動トリガーを廃止し、Actions タブの「Run workflow」で対象ブランチを選んで実行する運用に変更（FR-001 / FR-002 / FR-011 改定）。required checks によるブランチ保護は前提から外れるため設定しない（設定するとチェックが自動で走らずマージ不能になる）

## 概要

GitHub Actions 上に自動チェックのパイプラインを整備し、壊れたコード（lint 違反・型エラー・テスト失敗）が PR レビューや main ブランチに混入することを防ぐ。開発者は PR を出すだけで品質チェックの結果を PR 上で確認でき、レビュアーは機械的なチェックを人手で行わなくてよくなる。

本 feature は **CI（品質チェックの自動化）のみ** を対象とする。CD（デプロイ自動化）はデプロイ先確定後の後続 feature とする（2026-06-11 ユーザー確認済み）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - PR を出すと品質チェックが自動実行される (Priority: P1)

開発者として、PR を作成・更新したときに lint / フォーマット / 型チェック / 単体テストが自動で実行され、結果が PR 上のステータスとして表示されてほしい。落ちた場合はどのチェックが失敗したかすぐ特定したい。

**Why this priority**: CI の中核価値。これが無いと壊れた変更がレビューを素通りする。

**Independent Test**: lint 違反 / 型エラー / テスト失敗をそれぞれ含む PR を作成し、該当チェックが失敗としてレポートされること、修正 push で成功に変わることを確認できる。

**Acceptance Scenarios**:

1. **Given** チェックが全て通るブランチ、**When** PR を作成したとき、**Then** 全チェックが成功ステータスになる
2. **Given** 型エラーを含む変更、**When** PR を更新したとき、**Then** 型チェックのジョブが失敗し、PR 上で失敗箇所のログを確認できる
3. **Given** 単体テストが落ちる変更、**When** push したとき、**Then** テストジョブが失敗としてレポートされる
4. **Given** 実行中のチェックがあるブランチ、**When** 同じ PR に続けて push したとき、**Then** 古い実行はキャンセルされ最新コミットのみ検証される

---

### User Story 2 - main ブランチの健全性を常時保証する (Priority: P2)

開発者として、main へのマージ（push）時にも同じチェックが実行され、main が常にグリーンであることを確認したい。

**Why this priority**: PR チェックをすり抜けるケース（直 push・マージ競合後の状態）への保険。

**Independent Test**: main への push でワークフローが起動し、結果がコミットステータスに反映されることを確認できる。

**Acceptance Scenarios**:

1. **Given** main ブランチ、**When** マージコミットが push されたとき、**Then** 品質チェック一式が自動実行される
2. **Given** main のチェックが失敗した、**When** 結果を確認するとき、**Then** どのコミットで壊れたかが特定できる

---

### User Story 3 - 重いテスト（E2E / a11y）を main マージ時に自動実行する (Priority: P3)

開発者として、ブラウザを使う E2E / アクセシビリティテスト（DB 起動とテストユーザーが必要）が main へのマージ時に自動実行され、画面フローの退行に気づきたい。PR では軽量チェックのみで高速に回す（2026-06-11 ユーザー確認済み: 重いテストは main マージ時のみ）。

**Why this priority**: 価値は高いが実行時間とセットアップコストが大きく、軽量チェック（US1）が安定稼働してからで良い。

**Independent Test**: main への push で、CI 上にローカル DB がセットアップされ、シードユーザーでログインする E2E が成功することを確認できる。

**Acceptance Scenarios**:

1. **Given** main へのマージ、**When** フルテストが実行されたとき、**Then** DB 起動 → シード投入 → ブラウザテスト（E2E / a11y / Storybook テスト）が自動で完了する
2. **Given** 画面の退行（a11y 違反等）を含むマージ、**When** フルテストが実行されたとき、**Then** 該当テストが失敗としてレポートされ、壊したコミットを特定できる

---

### Edge Cases

- 依存パッケージのインストールが失敗した場合 → 各ジョブが npm ci ステップで独立に失敗する（ジョブは完全並列で依存なし）、セットアップ失敗として明確にレポートされる
- チェックが外部要因（ネットワーク等）で不安定に失敗した場合 → 開発者が再実行できる
- ワークフロー定義自体に構文エラーがある場合 → PR 上でワークフローの起動失敗が確認できる
- フォークからの PR（シークレットが渡らない）→ シークレット不要のチェックのみで構成し、影響を受けない

## Requirements *(mandatory)*

### Functional Requirements

#### トリガー

- **FR-001**: 品質チェック一式は手動実行（workflow_dispatch）で、任意のブランチを対象に実行できなければならない（2026-07-17 改定。旧: PR の作成・更新時に自動実行）
- **FR-002**: 削除（2026-07-17 改定）。main push の自動実行は手動運用への移行で廃止
- **FR-003**: システムは、同一 PR への連続 push 時に古い実行をキャンセルし、最新コミットのみを検証しなければならない（CI リソースの節約）

#### 品質チェックの内容

- **FR-004**: システムは、以下を独立に判別できる形で実行しなければならない: コードスタイル / フォーマット検査、型検査、単体テスト（カバレッジ閾値検証を含む）
- **FR-005**: システムは、DB スキーマの静的検査（マイグレーションの lint）を実行しなければならない
- **FR-006**: 各チェックの成否は PR のステータスとして個別に表示され、失敗時はログから原因箇所を特定できなければならない

- **FR-011**: 重いテスト（E2E / a11y / Storybook テスト）は軽量チェック（CI）とは別ワークフローとして手動実行できなければならない（2026-07-17 改定。旧: main push 時のみ自動実行）

#### 実行環境・性能

- **FR-007**: システムは、依存関係のキャッシュを利用して実行時間を短縮しなければならない
- **FR-008**: システムは、シークレットを必要とせずに PR チェックを完了できなければならない（フォーク PR でも動作する構成）

#### 運用

- **FR-009**: 開発者は、失敗したチェックを GitHub 上から再実行できなければならない
- **FR-010**: ワークフローの定義はリポジトリ内でバージョン管理され、変更は PR レビューの対象でなければならない

### Key Entities

- **ワークフロー定義**: リポジトリ管理される CI 設定。トリガー・ジョブ・キャッシュ戦略を記述する
- **チェック結果**: PR / コミットに紐づくステータス。ジョブ単位で成否とログを持つ

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: PR 作成から軽量チェック（lint / 型 / 単体テスト）の結果表示まで 10 分以内に完了する
- **SC-002**: 壊れた変更（lint 違反・型エラー・テスト失敗）を含む PR が、チェック失敗として 100% 検出される
- **SC-003**: チェック済みの main ブランチでローカル検証（型チェック・テスト）が常に成功する（CI とローカルの結果が一致する）
- **SC-004**: 同一 PR への連続 push で並走する重複実行が 0 件になる

## Assumptions

- 対象リポジトリは GitHub でホストされており、GitHub Actions が利用可能（無料枠 or 既存プラン内）
- チェック内容は既存のローカルコマンド（lint / format / type-check / unit test / DB lint）をそのまま CI 化する。新しい検査の追加は対象外
- マージブロック（branch protection / required checks の設定）は GitHub リポジトリ設定での手動作業とし、手順をドキュメント化する
- カバレッジ閾値は既存のテスト設定（70%）を変更しない
- Dependabot / 自動リリース・バージョニング・通知連携（Slack 等）は対象外

## Out of Scope（本 feature では扱わない）

- CD（デプロイ自動化）。デプロイ先確定後の後続 feature とする
- 自動リリース / タグ付け / changelog 生成
- 通知連携（Slack / メール）
- パフォーマンス計測・ビジュアルリグレッションテスト
- セルフホストランナーの構築
