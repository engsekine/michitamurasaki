# Feature Specification: 認証（メール + パスワード）

**Feature Branch**: `001-auth`

**Created**: 2026-06-10

**Status**: In Progress

**Input**: 既存仕様書からの移行

## User Scenarios & Testing *(mandatory)*

### User Story 1 - サインアップ（アカウント作成） (Priority: P1)

新規ユーザーとして、姓名・ニックネーム・生年月日・性別・メールアドレス・パスワードを入力してアカウントを作成し、ダイビングログを残せるようになりたい。

**Why this priority**: アカウントが存在しなければ他のすべての機能（ログイン・ログアウト・パスワードリセット・ダイブログ記録）が成立しない。プロダクトの入口となる最重要ストーリー。

**Independent Test**: `/signup` でフォームを送信し、確認メール（ローカルでは Inbucket）内のリンクをクリックして TOP（`/`）に到達できることを確認すれば、単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 未登録のユーザーが `/signup` を開いている、**When** 姓・名（漢字）、姓・名（ローマ字）、ニックネーム、生年月日、性別、メール、パスワードを正しく入力して送信する、**Then** システムは Supabase にユーザーを作成して確認メールを送信し、同時に `public.user_details` に姓名・ニックネーム・生年月日・性別を保存する
2. **Given** サインアップ要求が成功した直後、**When** 画面が更新される、**Then** 「確認メールを送信しました」と入力されたメールアドレスが表示される（この時点ではログイン状態にしない）
3. **Given** 確認メールが届いている、**When** ユーザーがメール内のリンクをクリックする、**Then** システムは `/api/auth/callback` でセッションを発行し TOP（`/`）にリダイレクトする
4. **Given** 確認リンクが無効または期限切れである、**When** ユーザーがそのリンクを開く、**Then** システムは `/login?error=auth_callback_failed` にリダイレクトする
5. **Given** `/signup` のフォーム、**When** 姓または名が未入力か 50 文字を超えている、**Then** システムはエラーメッセージを表示しサインアップを拒否する
6. **Given** `/signup` のフォーム、**When** 姓（ローマ字）または名（ローマ字）が半角英字以外を含むか 50 文字を超えている、**Then** システムはエラーメッセージを表示しサインアップを拒否する
7. **Given** `/signup` のフォーム、**When** ニックネームが未入力か 50 文字を超えている、**Then** システムはエラーメッセージを表示しサインアップを拒否する
8. **Given** `/signup` のフォーム、**When** 生年月日が未入力・未来日付・1900-01-01 より前のいずれかである、**Then** システムはエラーメッセージを表示しサインアップを拒否する
9. **Given** `/signup` のフォーム、**When** パスワードが 12 文字未満・72 文字超、または英大文字・英小文字・数字のいずれかを含まない、**Then** システムはエラーメッセージを表示しサインアップを拒否する
10. **Given** 既に登録済みのメールアドレスがある、**When** 同じメールアドレスでサインアップする、**Then** システムは「このメールアドレスは既に登録されています」を表示する

---

### User Story 2 - ログイン / ログアウト (Priority: P2)

既存ユーザーとして、ログインして自分のログにアクセスしたい。また、ログインしたユーザーとして安全にログアウトしたい。

**Why this priority**: アカウント作成後にサービスを継続利用するための基本動線。サインアップ（P1）が前提となるため P2。

**Independent Test**: 確認済みアカウントを用意し、`/login` での認証成功 → TOP（`/`）表示 → ログアウト → `/login` リダイレクトの一連を確認すれば単独で検証できる。

**Acceptance Scenarios**:

1. **Given** メール確認済みのユーザーが `/login` を開いている、**When** 正しい認証情報を入力して送信する、**Then** システムはセッションを作成し TOP（`/`）にリダイレクトする
2. **Given** `/login` のフォーム、**When** 誤った認証情報を入力して送信する、**Then** システムは「メールアドレスまたはパスワードが間違っています」を表示する
3. **Given** ログインに連続して失敗している、**When** さらにログインを試行する、**Then** Supabase のレート制限に従い一時的にロックされる
4. **Given** ログイン済みのユーザー、**When** ログアウトボタンを押す、**Then** システムはセッションを破棄し `/login` にリダイレクトする

---

### User Story 3 - 認証ガード (Priority: P2)

未認証のユーザーとして保護されたページに到達できないこと、また認証済みのユーザーとして認証ページに迷い込まないことを期待する。

**Why this priority**: 認証機能のセキュリティ境界そのもの。ログイン（US2）と同時期に成立している必要がある。

**Independent Test**: 未認証ブラウザで `/dives` にアクセスしてリダイレクトを確認し、認証済みブラウザで `/login` `/signup` にアクセスしてリダイレクトを確認すれば単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 未認証のユーザー、**When** `/dives` 配下の URL にアクセスする、**Then** システムは `/login` にリダイレクトする
2. **Given** 認証済みのユーザー、**When** `/login` または `/signup` にアクセスする、**Then** システムは TOP（`/`）にリダイレクトする

---

### User Story 4 - パスワードリセット (Priority: P3)

パスワードを忘れたユーザーとして、メール経由でパスワードをリセットし、再びログインできるようになりたい。

**Why this priority**: 利用継続のためのリカバリ動線だが、初期リリースの主動線（サインアップ・ログイン）の後でも価値を損なわない。

**Independent Test**: `/reset-password` でメールアドレスを送信し、リセットメール（ローカルでは Inbucket）から新パスワードを設定して `/login` に戻れることを確認すれば単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 登録済みユーザーが `/reset-password` を開いている、**When** メールアドレスを入力して送信する、**Then** システムはリセットリンクを含むメールを送信する
2. **Given** `/reset-password` のフォーム、**When** 登録されていないメールアドレスを入力して送信する、**Then** 情報漏洩防止のため、登録済みの場合と同じ成功メッセージを表示する
3. **Given** リセットメールが届いている、**When** リンクから新パスワードを設定する、**Then** システムはパスワードを更新し `/login` にリダイレクトする
   > 注記: 実装済み（2026-07-02 / T011）。リセットリンクは `/api/auth/callback?next=/update-password` 経由で新パスワード設定ページへ遷移する

---

### Edge Cases

- 確認リンクが無効・期限切れの場合 → `/login?error=auth_callback_failed` にリダイレクトする
- 既に登録済みのメールアドレスでサインアップした場合 → 「このメールアドレスは既に登録されています」を表示する
- 未登録メールアドレスでパスワードリセットを要求した場合 → 情報漏洩防止のため成功メッセージを表示する（登録有無を判別させない）
- ログインに連続失敗した場合 → Supabase のレート制限に従い一時的にロックされる
- サインアップ成功直後はログイン状態にしない（メール確認完了までセッションを発行しない）
- 性別が未選択のままの場合 → 未選択を許容せずデフォルトは「未回答」とする

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは `/signup` で姓・名（漢字）、姓・名（ローマ字）、ニックネーム、生年月日、性別、メールアドレス、パスワードを受け付け、Supabase Auth にユーザーを作成して確認メールを送信しなければならない
- **FR-002**: システムはサインアップ時に `public.user_details` へ姓名・ニックネーム・生年月日・性別を保存しなければならない
- **FR-003**: システムは姓・名（漢字）が未入力または 50 文字超の場合、エラーメッセージを表示しサインアップを拒否しなければならない
- **FR-004**: システムは姓・名（ローマ字）が半角英字以外を含む、または 50 文字超の場合、エラーメッセージを表示しサインアップを拒否しなければならない
- **FR-005**: システムはニックネームが未入力または 50 文字超の場合、エラーメッセージを表示しサインアップを拒否しなければならない
- **FR-006**: システムは生年月日が未入力・未来日付・1900-01-01 より前の場合、エラーメッセージを表示しサインアップを拒否しなければならない
- **FR-007**: システムは性別を「男性 / 女性 / 未回答」の 3 択で受け付け、未選択を許容せずデフォルトを「未回答」としなければならない
- **FR-008**: システムはパスワードを 12 文字以上 72 文字以内かつ英大文字・英小文字・数字をそれぞれ 1 文字以上含むものとして受け付け、満たさない場合はエラーメッセージを表示しサインアップを拒否しなければならない。強度方針は長さ重視（NIST SP 800-63B 準拠）＋英大小・数字の必須化とし、記号は必須にしない（Supabase の `password_requirements = "lower_upper_letters_digits"` と一致）。これにより Google(Chrome) / iCloud の自動生成パスワードはそのまま通過する（上限 72 文字は Supabase Auth の bcrypt 制約に合わせる）
- **FR-009**: システムは登録済みメールアドレスでのサインアップ時に「このメールアドレスは既に登録されています」を表示しなければならない
- **FR-010**: システムはサインアップ要求成功時に「確認メールを送信しました」と入力されたメールアドレスを表示し、この時点ではログイン状態にしてはならない
- **FR-011**: システムは確認メール内リンクのクリック時に `/api/auth/callback` でセッションを発行し TOP（`/`）にリダイレクトしなければならない
- **FR-012**: システムは確認リンクが無効・期限切れの場合 `/login?error=auth_callback_failed` にリダイレクトしなければならない
- **FR-013**: システムは `/login` で正しい認証情報が入力されたとき、セッションを作成し TOP（`/`）にリダイレクトしなければならない
- **FR-014**: システムは認証情報が誤っているとき「メールアドレスまたはパスワードが間違っています」を表示しなければならない
- **FR-015**: システムはログインの連続失敗時、Supabase のレート制限に従い一時的にロックしなければならない
- **FR-016**: システムはログアウト操作時にセッションを破棄し `/login` にリダイレクトしなければならない
- **FR-017**: システムは `/reset-password` でメールアドレスが入力されたとき、リセットリンクを含むメールを送信しなければならない
- **FR-018**: システムは未登録メールアドレスでのリセット要求でも、情報漏洩防止のため成功メッセージを表示しなければならない
- **FR-019**: システムはリセットリンク経由で新パスワードが設定されたとき、パスワードを更新し `/login` にリダイレクトしなければならない（実装済み 2026-07-02: `/update-password` ページ + `updatePassword` アクション。更新後はサインアウトして `/login` へ）
- **FR-020**: システムは未認証ユーザーの `/dives` 配下へのアクセスを `/login` にリダイレクトしなければならない
- **FR-021**: システムは認証済みユーザーの `/login` `/signup` へのアクセスを TOP（`/`）にリダイレクトしなければならない

### Key Entities

- **users**: アプリ側のユーザー識別子。`auth.users(id)` を主キーとして共有し、「アプリ側の user として存在する」ことだけを表す（詳細は [data-model.md](data-model.md) を参照）
- **user_details**: ユーザーのプロフィール属性（姓名・ニックネーム・生年月日・性別・身長・体重）。`users` と 1:1（詳細は [data-model.md](data-model.md) を参照）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新規ユーザーがサインアップフォーム送信から確認メールのリンククリックを経て TOP（`/`）に到達するまでの一連の動線を、追加のサポートなしで完了できる
- **SC-002**: requirements 由来の全受け入れ条件（バリデーション・リダイレクト・メッセージ表示）が E2E テスト（Playwright）で再現・合格する
- **SC-003**: 未認証状態での保護ルート（`/dives` 配下）へのアクセスが 100% `/login` にリダイレクトされる
- **SC-004**: 未登録メールアドレスへのパスワードリセット要求に対し、レスポンス内容から登録有無を判別できない（登録済みと同一の成功メッセージを返す）
- **SC-005**: ローカル開発環境において、確認メール・リセットメールが Inbucket（`http://127.0.0.1:54324`）で確認できる

## Assumptions

- 認証基盤として Supabase Auth を利用する（パスワードハッシュ・レート制限・メール送信は Supabase に委譲）
- Supabase の `enable_confirmations = true` が設定されている（`supabase/config.toml` 参照）
- ローカル開発時のメール確認は Inbucket（`http://127.0.0.1:54324`）で行う
- `public.users` / `public.user_details` への行挿入は `auth.users` の insert トリガー（`handle_new_user`）が行い、アプリケーションコードから直接 insert しない
- 以下は Phase 1 の対象外:
  - ソーシャルログイン
  - MFA / 2FA
  - メールアドレス変更
  - アカウント削除
  - 招待機能
