# Feature Specification: 通知機能（アプリ内通知）

**Feature Branch**: `025-notifications`

**Created**: 2026-07-02

**Status**: Draft

**Input**: User description: "通知系機能実装"

## Clarifications

### Session 2026-07-02

- Q: 既読になる条件（一覧表示だけで既読か、タップで既読か） → A: 個別にタップした通知のみ既読 + 「すべて既読にする」ボタン（一覧を開いただけでは未読のまま。リマインドを見落とさない）
- Q: 通知一覧の提供形態（専用ページ / ドロップダウン / 併用） → A: 専用ページのみ。ヘッダーのベルアイコン（未読バッジ付き）から遷移する。ドロップダウンは設けない
  - **変更（feat/design-change・2026-07-08）**: ベルを押すとページ遷移なしのシート（パネル）で最新の通知を確認できる併用型に変更。専用ページ（`/notifications`）は全件・追加読み込み・すべて既読の場として維持し、シート内の「すべての通知を見る」から遷移する
- Q: 集約済みフォロー通知を既読にした後に再フォローされた場合 → A: 既読のまま維持（発生日時のみ更新）。再フォローで未読に復活させない（解除→再フォロー連打のスパム化防止）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ソーシャルイベントのアプリ内通知 (Priority: P1)

利用者は、自分に関係する出来事（誰かにフォローされた・誰かのログに同行バディとしてタグ付けされた）が起きたことを、アプリを開いたときに気づける。ヘッダーの通知アイコンに未読件数が表示され、通知一覧から相手のプロフィールや該当のログへ直接移動できる。

**Why this priority**: フォロー・バディタグ（021）はすでに使える機能だが、相手に何も知らされないため「つながり」が一方通行で終わっている。ソーシャル機能の価値を成立させる最小の通知がこの 2 種であり、通知の基盤（受信・一覧・未読・既読）もこのストーリーで完成する。

**Independent Test**: ユーザー B がユーザー A をフォロー（またはバディにタグ付け）したあと、ユーザー A がアプリを開くと未読バッジが付き、通知一覧に「B さんにフォローされました」が新しい順で表示され、タップで B のプロフィール（またはログ詳細）に遷移できることで単独検証できる。

**Acceptance Scenarios**:

1. **Given** ユーザー A がログイン済み、**When** ユーザー B が A をフォローする、**Then** A の通知一覧に「フォローされた」通知が追加され、未読件数が 1 増える
2. **Given** ユーザー B が自分の公開ログにユーザー A を同行バディとしてタグ付けした、**When** A が通知一覧を開く、**Then** 「B さんのログにバディとして追加されました」が表示され、タップで該当ログ詳細へ遷移できる
3. **Given** 未読通知が 3 件ある、**When** 通知一覧を開く、**Then** 未読件数は変わらない（一覧表示だけでは既読にならない）。個別の通知をタップするとその通知だけが既読になり未読件数が減り、「すべて既読にする」で残りも一括で既読にできる
4. **Given** 通知が 1 件もない、**When** 通知一覧を開く、**Then** 「通知はありません」の空状態が表示される
5. **Given** ユーザー B が A をフォロー解除して再フォローを繰り返す、**When** A が通知一覧を開く、**Then** 同じ相手からのフォロー通知は最新の 1 件だけが表示される（連打によるスパム化を防ぐ）。A が既にその通知を既読にしていた場合、再フォローで未読には戻らない

---

### User Story 2 - 予定・メンテナンスのリマインド通知 (Priority: P2)

利用者は、自分で登録したダイビング予定の当日と、レギュレーターのオーバーホール（OH）期限の到達を、通知で思い出せる。予定の通知からはその予定の詳細（ログへの移動導線がある画面）へ、OH の通知からは機材設定へ移動できる。

**Why this priority**: 予定（004/024）と OH 管理（003）は登録した後に見返さないと意味がない「時限性」の機能で、リマインドがあると実用度が大きく上がる。ただしソーシャル通知（P1）の基盤の上に載る時限イベントであり、単体では通知基盤ごと作る必要があるため P2 とする。

**Independent Test**: 予定日が今日のダイビング予定を持つユーザーがアプリを開くと「今日は〇〇のダイビング予定日です」通知が届いていること、OH 期限を過ぎたレギュレーターを持つユーザーに「OH 期限が到来しました」通知が届いていることで単独検証できる。

**Acceptance Scenarios**:

1. **Given** ユーザーが予定日 = 今日のダイビング予定を持っている、**When** その日にアプリを利用する、**Then** 予定日当日の通知が 1 回だけ届き、タップで予定詳細へ遷移できる
2. **Given** レギュレーターの OH 期限（次回 OH 予定日）が到来した、**When** 利用者がアプリを利用する、**Then** OH 期限の通知が 1 回だけ届き、タップで機材設定へ遷移できる
3. **Given** 予定日当日の通知を受け取ったあと予定をログへ移動した、**When** 通知一覧の同じ通知を再度開く、**Then** 移動済みでもエラーにならず適切な画面（ログ詳細または予定一覧）へ案内される

---

### User Story 3 - 通知設定（種別ごとの ON/OFF） (Priority: P3)

利用者は、設定画面から通知の種別（フォロー / バディタグ / 予定リマインド / OH リマインド）ごとに受け取りの ON/OFF を切り替えられる。OFF にした種別の通知は以後生成されない。

**Why this priority**: 通知が増えるほど「望まない通知を止めたい」ニーズが生まれるが、v1 の通知種別は少なく既定 ON で困る利用者は限定的。基盤と通知種別が揃ってからで十分なため P3。

**Independent Test**: 設定画面でフォロー通知を OFF にしたあと、他ユーザーにフォローされても通知が追加されないこと、ON に戻すと再び通知されることで単独検証できる。

**Acceptance Scenarios**:

1. **Given** 通知設定は既定ですべて ON、**When** フォロー通知を OFF にして他ユーザーにフォローされる、**Then** 通知は追加されない（フォロー自体は成立する）
2. **Given** フォロー通知を OFF にしていた、**When** ON に戻して他ユーザーにフォローされる、**Then** 通知が追加される（OFF 期間中のイベントは遡って通知されない）

---

### Edge Cases

- 自分自身の操作（自分のログへの自分の操作等）では通知を生成しない。なお自己フォロー・所有者の自己バディタグは既存機能側で禁止済み
- 通知の発生元ユーザーが退会した場合、通知は表示され続けるが、遷移先が存在しないときはエラーにせず案内（プロフィールが見つからない旨）を表示する
- 通知の対象リソース（ログ・予定）が削除・非公開化された場合、通知からの遷移はエラー画面ではなく適切なフォールバック（一覧やホーム）に案内する
- バディタグをタグ付けされた本人が外した（オプトアウトした）あとは、同じログへの再タグ付けが既存仕様でブロックされるため、再通知も発生しない
- 未読バッジは複数タブ・複数端末間で厳密なリアルタイム同期を要求しない（画面遷移や再読み込みで最新化されれば良い）
- 通知が大量にある場合も一覧は快適に閲覧できる（ページング等で全件を一度に読み込まない）
- 予定日リマインドは、予定日を過ぎてから登録された予定（過去日の予定）には発生させない

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、ユーザーがフォローされたとき、フォローされた側にアプリ内通知を生成しなければならない
- **FR-002**: システムは、ユーザーが他ユーザーのログに同行バディ（登録ユーザー参照）としてタグ付けされたとき、タグ付けされた側にアプリ内通知を生成しなければならない。フリーテキストのバディ名では通知しない
- **FR-003**: ユーザーは、自分宛の通知を専用の通知一覧ページで新しい順に閲覧できなければならない（ドロップダウン形式は採用しない）。一覧は全件を一度に読み込まず、段階的に閲覧できること
- **FR-004**: システムは、全認証済みページ共通のヘッダーに通知アイコンを置き、未読通知の件数をバッジ表示しなければならない。アイコンを押すとページ遷移なしのシートで最新の通知を確認でき、通知のタップで既読化して対象へ遷移できること。シート内の導線から通知一覧ページへ遷移できること。件数が多い場合は上限表示（「9+」）でよい（feat/design-change でリンク → シート表示に変更）
- **FR-005**: 通知は個別にタップ（開封）したときにのみ既読になる。一覧を表示しただけでは既読にしない。あわせて「すべて既読にする」による一括既読化を提供しなければならない
- **FR-006**: 通知は、種別に応じた遷移先（フォロー → 相手のプロフィール、バディタグ → 該当ログ詳細、予定リマインド → 予定詳細、OH リマインド → 機材設定）へ移動できなければならない
- **FR-007**: システムは、本人の操作に起因するイベントでは本人へ通知を生成してはならない
- **FR-008**: システムは、同一の相手からの同一種別の通知を最新 1 件に集約し、重複した通知でスパム化させてはならない（フォロー解除→再フォローの連打等）。集約時、既読済みの通知は既読のまま維持する（発生日時のみ更新し、未読に復活させない）
- **FR-009**: システムは、予定日当日になったダイビング予定について、その所有者に 1 回だけリマインド通知を生成しなければならない（過去日で登録された予定は対象外）
- **FR-010**: システムは、レギュレーターの OH 期限（次回 OH 予定日）が到来したとき、その所有者に 1 回だけリマインド通知を生成しなければならない
- **FR-011**: ユーザーは、通知種別ごとに受け取りの ON/OFF を設定できなければならない。既定はすべて ON とし、OFF の種別は通知を生成しない（OFF 期間中のイベントは ON に戻しても遡及しない）
- **FR-012**: 通知の発生元（ユーザー・ログ・予定）が削除等で存在しなくなった場合でも、通知一覧の表示および遷移操作はエラーにせず、適切な案内またはフォールバック先へ誘導しなければならない
- **FR-013**: システムは、通知を無期限に蓄積せず、一定期間（90 日）経過した通知を自動的に削除してよい
- **FR-014**: 通知は本人のみが閲覧・既読化できなければならない。他ユーザーの通知の閲覧・操作はいかなる手段でもできてはならない

### Key Entities

- **通知**: 受信者、種別（フォロー / バディタグ / 予定リマインド / OH リマインド）、発生元ユーザー（いる場合）、関連リソース（ログ / 予定 / 機材。いる場合）、既読状態、発生日時を持つ。受信者本人だけが読める
- **通知設定**: ユーザーごと・通知種別ごとの受け取り ON/OFF。未設定は ON とみなす

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: フォロー・バディタグの発生から 1 分以内に、受信者の次回画面表示で未読バッジに反映される
- **SC-002**: 利用者はどの画面からでも 2 操作以内（通知アイコン → 通知タップ）で通知の対象に到達できる
- **SC-003**: 既読化の操作（個別・一括）は即座に一覧とバッジへ反映され、再読み込み後も維持される
- **SC-004**: 通知が 1,000 件あるユーザーでも通知一覧の初回表示が体感遅延なく（2 秒以内に）表示される
- **SC-005**: 他ユーザーの通知を閲覧・既読化できた事例が 0 件である
- **SC-006**: 通知を OFF にした種別で通知が生成された事例が 0 件である

## Assumptions

- **v1 はアプリ内通知のみ**とする。メール通知・プッシュ通知はスコープ外（メール通知を将来追加する場合は、022 のメール配信許可（オプトイン）に従う）
- リアルタイム配信（開いている画面への即時プッシュ）は要求しない。画面表示・遷移のタイミングで最新の通知・未読数が取得できれば十分とする
- 通知の対象イベントは既存機能（021 フォロー / バディタグ、004・024 ダイビング予定、003 レギュレーター OH）で発生するものに限る。いいね・コメント等の新規ソーシャル機能は本仕様のスコープ外
- リマインド通知（US2）の「当日」「期限到来」の判定は、既存機能と同じ JST（日本標準時）の暦日基準とする
- 通知の保持期間 90 日（FR-013）は運用しながら調整してよい初期値とする
- タグ付け通知は公開・非公開ログのどちらでも生成される（タグ付けされた本人は自分宛タグを常に確認・管理できる既存仕様に合わせる）
