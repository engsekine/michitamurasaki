# Feature Specification: ログ枠の有料化（デイリーボーナス + 買い切りログパック）

**Feature Branch**: `026-log-monetization`

**Created**: 2026-07-02

**Status**: Draft

**Input**: User description: "有料化 / 無料ユーザー：デイリーボーナス→1日1ログ追加できる量を増やす / 広告なし、ログは買い切りにしたい例えば10ログ 300円とか"

## 概要

ダイビングログの作成数を「ログ枠（クレジット）」で管理する収益化機能。無料ユーザーはデイリーボーナスで 1 日 1 枠ずつログ枠を獲得でき、まとまった枠が必要なユーザーは買い切りのログパック（お試し 10 枠 480 円 / おすすめ 30 枠 1,200 円 / たっぷり 100 枠 3,000 円）を購入する。広告は一切表示しない方針で、収益はログパックの買い切り販売のみで得る。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 無料ユーザーのログ枠とデイリーボーナス (Priority: P1)

無料ユーザーとしてアプリを利用すると、ログ作成に「ログ枠」を 1 つ消費する。ログ枠はデイリーボーナスとして 1 日 1 枠付与されるため、毎日 1 本ペースのログ付けであれば無料のまま使い続けられる。残枠が 0 の状態ではログを作成できず、翌日のボーナスを待つか購入を案内される。

**Why this priority**: ログ枠という消費・付与の仕組みがすべての土台であり、これがないと購入機能も意味を持たない。また無料ユーザーの体験を先に確定させないと、既存ユーザーの離脱リスクを制御できない。

**Independent Test**: 購入機能なしで単独テスト可能。残枠がある状態でログ作成→枠が 1 減る、残枠 0 でログ作成不可、日付が変わるとボーナスで +1 されることを確認できる。

**Acceptance Scenarios**:

1. **Given** 残枠が 1 以上あるユーザー, **When** ログを新規作成する, **Then** ログが保存され残枠が 1 減る
2. **Given** 残枠が 0 のユーザー, **When** ログを新規作成しようとする, **Then** 作成できず「残枠がない」旨とデイリーボーナス・購入の案内が表示される
3. **Given** 当日分のデイリーボーナスを未獲得のユーザー, **When** その日（JST）はじめてアプリを訪問する, **Then** ログ枠が自動的に 1 増え、同日中に再度付与されることはない
4. **Given** ログ枠を消費して作成した既存ログ, **When** そのログを編集・閲覧する, **Then** 追加の枠消費なしで操作できる

---

### User Story 2 - ログパックの買い切り購入 (Priority: P2)

デイリーボーナスだけでは足りないユーザー（旅行で 1 日に複数本潜る、過去のログをまとめて移行したい等）が、買い切りのログパック（お試し 10 枠 480 円 / おすすめ 30 枠 1,200 円 / たっぷり 100 枠 3,000 円 の 3 種）を購入してログ枠をまとめて獲得する。購入した枠に有効期限はなく、サブスクリプションではないため解約や自動更新の概念もない。

**Why this priority**: 本機能の収益源。ただし US1 のログ枠の仕組みが先に存在しないと成立しないため P2。

**Independent Test**: US1 実装済みの状態で、購入フローを完了すると残枠がパックの枠数分増えることを単独で確認できる。

**Acceptance Scenarios**:

1. **Given** ログインユーザー, **When** ログパック（例: おすすめ 30 枠 1,200 円）の購入を完了する, **Then** 残枠がパックの枠数分（30）増え、購入完了が画面で確認できる
2. **Given** 決済が失敗した購入, **When** 決済プロバイダからエラーが返る, **Then** ログ枠は付与されず、ユーザーに失敗理由と再試行の案内が表示される
3. **Given** 同一の決済が重複して通知されたケース, **When** システムが購入結果を処理する, **Then** ログ枠は 1 回分（購入パックの枠数）だけ付与される
4. **Given** 残枠 0 でログ作成をブロックされたユーザー, **When** 案内から購入ページへ進む, **Then** 離脱せずそのまま購入を完了してログ作成に戻れる

---

### User Story 3 - 残枠の可視化と購入履歴 (Priority: P3)

ユーザーは自分のログ枠の残数をいつでも確認でき、「あと何本ログを書けるか」を把握した上でダイビング旅行の前などに計画的に購入できる。また過去の購入履歴（日時・パック内容・金額）を確認できる。

**Why this priority**: 透明性と安心感のための補助機能。US1/US2 が動作していれば後追いで提供しても価値が損なわれない。

**Independent Test**: 残枠・履歴の表示のみを単独でテスト可能。ボーナス獲得・消費・購入の各操作後に表示が正しく更新されることを確認できる。

**Acceptance Scenarios**:

1. **Given** ログインユーザー, **When** ログ作成画面やダッシュボードを開く, **Then** 現在の残枠数が表示される
2. **Given** 購入経験のあるユーザー, **When** 購入履歴画面を開く, **Then** 各購入の日時・内容（枠数）・金額が一覧できる
3. **Given** 残枠が増減する操作（ボーナス獲得・ログ作成・購入）, **When** 操作が完了する, **Then** 表示される残枠が即座に最新の値へ更新される

---

### Edge Cases

- 日付境界: デイリーボーナスの「1 日」は日本時間（JST）の暦日で判定する。日をまたいだ瞬間に未獲得なら新しい日の分を獲得できる
- ログ削除: ログを削除しても消費済みの枠は返却されない（作成→削除の繰り返しによる枠の実質無限化を防ぐ）
- 予定→ログ移動（024）: ダイビング予定をログへ移動する操作も「ログの新規作成」としてログ枠を 1 消費する。残枠 0 の場合は移動できず案内を表示する
- 決済完了と枠付与のタイムラグ: 決済プロバイダからの完了通知が遅延した場合でも、通知受領後に枠が付与され、ユーザーには「反映待ち」であることが分かる
- 残枠 0 での同時多重リクエスト: 残枠 1 で同時に複数のログ作成リクエストが発生しても、枠を超えてログが作成されることはない
- 返金: 決済プロバイダ経由で返金が行われた場合、未消費分の枠を上限として残枠から差し引く（残枠がマイナスになる場合は 0 で止め、以後のログ作成をブロックする）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムはユーザーごとにログ枠（残数）を管理し、ログの新規作成 1 件につき 1 枠を消費しなければならない
- **FR-002**: 残枠が 0 のユーザーはログを新規作成できず、デイリーボーナスと購入への案内が表示されなければならない
- **FR-003**: システムは無料・有料を問わず全ユーザーに、JST 暦日で 1 日 1 回、ログ枠 1 つをデイリーボーナスとして付与しなければならない。付与はその日はじめてアプリを訪問（認証済みアクセス）した時点で自動的に行われ、受け取り操作は不要とする
- **FR-004**: デイリーボーナスで蓄積できるログ枠に保有上限は設けない（購入枠と同様に無制限・無期限に保持できる）
- **FR-005**: ユーザーは買い切りのログパック（お試し 10 枠 480 円 / おすすめ 30 枠 1,200 円 / たっぷり 100 枠 3,000 円）から 1 つを選んで購入でき、決済成功後に残枠へ選択パックの枠数が加算されなければならない
- **FR-006**: 購入したログ枠に有効期限を設けてはならない（買い切り）
- **FR-007**: 決済が完了していない購入に対して枠を付与してはならず、同一決済の重複処理による二重付与を防がなければならない
- **FR-008**: 新規登録ユーザーには初期無料枠として 10 枠を付与しなければならない。本機能の導入時点で既に登録済みのユーザーにも同様に 10 枠を付与する
- **FR-009**: 本機能の導入前に作成された既存ログは枠消費の対象外とし、そのまま閲覧・編集・削除できなければならない（遡及しない）
- **FR-010**: ログの編集・閲覧・削除・エクスポートは枠を消費してはならない（消費は新規作成のみ）
- **FR-011**: ログを削除しても消費済みの枠は返却されない
- **FR-012**: ダイビング予定からログへの移動（024 の機能）はログの新規作成として枠を 1 消費しなければならない
- **FR-013**: ユーザーは現在の残枠数をログ作成導線上で常に確認できなければならない
- **FR-014**: ユーザーは自分の購入履歴（購入日時・パック内容・金額）を確認できなければならない
- **FR-015**: アプリ内に広告を表示してはならない（無料ユーザーを含む全ユーザー）
- **FR-016**: 枠の増減（ボーナス付与・消費・購入・返金調整）はすべて記録され、残枠は記録から検証可能でなければならない

### Key Entities *(include if feature involves data)*

- **ログ枠残高**: ユーザーごとの現在利用可能なログ枠数。ボーナス付与・購入で増え、ログ新規作成で減る
- **枠取引履歴（レジャー）**: 枠の増減 1 件ごとの記録。種別（デイリーボーナス / 購入 / 消費 / 返金調整）、増減数、発生日時、関連ログ・関連購入への参照を持つ。残高はこの履歴の集計と常に一致する
- **購入**: ログパックの購入 1 件。購入者、パック内容（枠数）、金額、決済状態（処理中 / 完了 / 失敗 / 返金済み）、決済プロバイダ側の取引識別子を持つ
- **ログ（既存）**: 既存のダイビングログ。本機能導入後に新規作成されるものだけが枠消費と紐づく

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 毎日 1 本以下のペースでログを付ける無料ユーザーは、支払いなしで従来どおりログを作成し続けられる（デイリーボーナスのみで枠が途切れない）
- **SC-002**: ユーザーは残枠 0 の状態から 3 分以内にログパックの購入を完了し、ログ作成を再開できる
- **SC-003**: 決済成功から 1 分以内に残枠へ反映される（反映遅延による問い合わせが購入件数の 1% 未満）
- **SC-004**: 枠残高と取引履歴の不整合（二重付与・過剰消費）の発生件数が 0 である
- **SC-005**: アプリ内の広告表示箇所が 0 である
- **SC-006**: 機能リリース後 3 ヶ月で、月間アクティブユーザーの 3% 以上がログパックを 1 回以上購入する
- **SC-007**: 機能導入前から利用している既存ユーザーの既存ログに対する影響（閲覧・編集不可となる件数）が 0 件である

## Assumptions

- 価格・内容量は当初の単一パック（10 ログ 300 円）から 2026-07 の価格改定で 3 パック構成（お試し 10 枠 480 円 / おすすめ 30 枠 1,200 円 / たっぷり 100 枠 3,000 円）へ変更した。将来のパック追加・価格変更に耐えられるよう、仕様上はパック定義を固定値とみなさない
- デイリーボーナスの日付判定は日本時間（JST）の暦日とする（本アプリの主要ユーザーは日本在住の想定）
- 決済は Web 上のオンライン決済で行う（決済手段の詳細はプラン工程で決定する）。アプリストア課金は対象外
- 枠は「消費型クレジット」モデルとする。ログ削除による返却は行わない
- 既存ユーザーの導入時点の残枠は、初期無料枠（FR-008）と同じ扱いとする
- 返金はサポート対応（決済プロバイダのダッシュボード等）経由の例外運用とし、アプリ内にユーザー向け返金申請フローは設けない
- ボーナス枠の保有上限なしは意図的な選択である。無料で使い続けられる寛容さを優先し、購入は「今すぐまとまった枠が必要」なユーザー（旅行・過去ログ移行）向けと位置づける
- 広告なしは恒久方針であり、無料ユーザーへの広告表示による収益化は行わない（docs/product.md の将来構想にある「広告バナー設置」は本仕様で明示的に廃止する）
