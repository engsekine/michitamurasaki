# Feature Specification: デプロイパイプライン（GitHub Actions による stg / prod 自動反映）

**Feature Branch**: `028-deploy-pipeline`

**Created**: 2026-07-06

**Status**: Draft

**Input**: User description: "github actions経由でデプロイするci/cdを組みたい service-frontとadmin-frontはvercelにsupabaseはsupabaseにデプロイするように / developにマージされたらstg環境反映 / mainにマージされたらprod環境反映 / 必要な環境変数とかが合ったらreadmeに記載して readmeにデプロイの手順と解説を加えていって"

## Clarifications

- Session 2026-07-17: **全ワークフローを手動実行（workflow_dispatch）へ移行**。マージ（push）トリガーの自動デプロイを廃止し、Actions タブの「Run workflow」から実行する運用に変更（FR-001 / FR-002 改定）。誤ったブランチからのデプロイはワークフロー内のブランチガード（stg = develop / prod = main 固定）で防止する

## 概要

手動実行（workflow_dispatch）をトリガーに、3 つのデプロイ対象（service-front / admin-front → Vercel、データベース → Supabase）を反映する CI/CD パイプラインを構築する。stg は `develop`、prod は `main` をデプロイ元に固定する（2026-07-17 改定。当初はマージ連動の自動反映だった）。デプロイに必要な資格情報・環境変数の一覧と、初期セットアップ手順・運用解説を README に整備し、チームの誰でもデプロイの仕組みを理解・再現できる状態にする。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - develop マージで stg 環境へ自動反映 (Priority: P1)

開発者が機能ブランチの PR を `develop` にマージすると、追加の手作業なしにデータベースのマイグレーションが stg の Supabase プロジェクトへ適用され、service-front / admin-front の stg 環境が新しいコードで更新される。開発者は stg の URL を開いて動作確認できる。

**Why this priority**: 現在デプロイの仕組み自体が存在しない。まず stg で「マージ → 自動反映」の一連を成立させることが本機能の土台であり、prod（US2）は stg の複製 + 保護の追加で実現できる。

**Independent Test**: prod 設定なしで単独テスト可能。develop へダミー変更をマージし、stg の各 URL に変更が反映されること・マイグレーションが stg DB に適用されることを確認できる。

**Acceptance Scenarios**:

1. **Given** develop への PR がマージされた, **When** パイプラインが完走する, **Then** stg の service-front / admin-front に変更が反映され、未適用のマイグレーションが stg DB に適用されている
2. **Given** マイグレーションを含まない変更のマージ, **When** パイプラインが実行される, **Then** DB は変更されず（適用済みのまま）、アプリのみ更新される
3. **Given** マイグレーションの適用が失敗した, **When** パイプラインが停止する, **Then** アプリのデプロイは実行されず、失敗が GitHub 上で確認できる（古いスキーマ + 新しいアプリの不整合を防ぐ）
4. **Given** テスト（既存 CI）が失敗しているコミット, **When** develop にマージされた場合でも, **Then** デプロイは開始されない

---

### User Story 2 - main マージで prod 環境へ反映 (Priority: P2)

リリース担当者が `develop` から `main` への PR をマージすると、prod への反映パイプラインが起動する。指定した承認者が承認すると、prod の Supabase プロジェクトへマイグレーションが適用され、続いて service-front / admin-front の本番環境が更新される。承認するまで prod は一切変更されない。

**Why this priority**: 収益（026 ログ枠購入）を持つ本番環境の反映。US1 の仕組みを prod 用の資格情報 + 承認ゲートで複製する。

**Independent Test**: main へのマージで prod の各 URL に変更が反映されること、承認が完了するまで DB 変更が保留されることを確認できる。

**Acceptance Scenarios**:

1. **Given** main への PR がマージされた, **When** 承認者がデータベース反映を承認しパイプラインが完走する, **Then** prod のアプリ 2 つと DB に変更が反映される
2. **Given** マイグレーションを含む main へのマージ, **When** 承認者がまだ承認していない, **Then** DB とアプリの反映は保留され、承認まで prod は変更されない
3. **Given** 承認者が却下した, **When** パイプラインが中断される, **Then** prod は一切変更されず、中断が記録に残る
4. **Given** stg で検証済みの同一マイグレーション, **When** prod に適用される, **Then** stg と同じ結果（同一スキーマ）になる

---

### User Story 3 - デプロイ手順と環境変数の README 整備 (Priority: P3)

新しくチームに入った開発者（または将来の自分）が README を読むだけで、(1) デプロイの全体像（どのブランチがどの環境に反映されるか）、(2) 初期セットアップに必要な外部サービス側の準備と資格情報の一覧、(3) 障害時・手動デプロイ時の操作方法を理解できる。

**Why this priority**: パイプライン自体は US1/US2 で動くが、資格情報の設定方法が記録されていないと再現・引き継ぎができない。ユーザー要望に明示されたデリバラブル。

**Independent Test**: README の手順だけを見て、クリーンな状態から必要なシークレット・環境変数をすべて設定でき、値の取得元（どのサービスのどの画面か）が特定できる。

**Acceptance Scenarios**:

1. **Given** README のデプロイ節, **When** 必要な資格情報の表を参照する, **Then** すべてのシークレット・環境変数について「名前 / 用途 / 取得元 / 設定場所」が記載されている
2. **Given** ブランチ運用を知らない開発者, **When** README を読む, **Then** develop → stg / main → prod の対応と、リリースの流れ（develop → main への昇格）が理解できる
3. **Given** パイプラインの失敗, **When** README のトラブルシューティングを参照する, **Then** 再実行・手動デプロイの手順が分かる

---

### Edge Cases

- **マイグレーション失敗**: DB 反映が失敗したらアプリの反映は中止する（スキーマとコードの不整合防止）。失敗したマイグレーションの修正は「逆方向の新規マイグレーション」で行う（sql.md の方針どおり、down は書かない）
- **アプリのみの反映失敗**: DB 適用成功後にアプリの反映が失敗した場合、再実行でアプリのみ再デプロイできる（DB 適用は冪等 = 適用済みはスキップ）
- **同一ブランチへの連続マージ**: 後続の実行が前の実行を追い越さない（同一環境への同時デプロイは直列化またはキャンセルされる）
- **フロントのみ / DB のみの変更**: 変更に関係なくパイプラインは常に全対象を対象にしてよいが、DB 適用は未適用分のみ実行されるため二重適用は起きない
- **シークレットのローテーション**: 資格情報を差し替えても、リポジトリのコード変更なしに（設定画面の更新のみで）次回デプロイから有効になる
- **fork からの PR**: シークレットは fork の PR から参照できないこと（デプロイはマージ後のブランチ上でのみ実行）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: stg 環境への反映は手動実行（workflow_dispatch）で開始され、デプロイ元は `develop` ブランチに固定されなければならない（2026-07-17 改定。旧: develop push で自動開始）
- **FR-002**: prod 環境への反映は手動実行（workflow_dispatch）で開始され、デプロイ元は `main` ブランチに固定されなければならない（2026-07-17 改定。旧: main push で自動開始）
- **FR-003**: 反映対象は 3 つ: service-front（Vercel）・admin-front（Vercel）・データベースマイグレーション（Supabase）。データベースは stg / prod で**別の Supabase プロジェクト**に完全分離する。Vercel はアプリごとに 1 プロジェクトとし、stg は固定 URL の Preview 環境・prod は Production 環境として同一プロジェクト内で分離する
- **FR-004**: データベースの反映はアプリの反映より**先**に完了しなければならず、DB 反映が失敗した場合はアプリの反映を実行してはならない
- **FR-005**: マイグレーションの適用は冪等でなければならない（適用済みのものはスキップされ、再実行で二重適用されない）
- **FR-006**: prod への反映（DB・アプリのすべて）は、指定された承認者による**手動承認を経てから**実行されなければならない。承認は main マージ後のパイプライン上で 1 回行い、承認されるまで prod は一切変更されない
- **FR-007**: テスト（既存 CI 相当のチェック）が成功していることをデプロイの前提条件とし、失敗コミットは環境へ反映されない
- **FR-008**: 資格情報（デプロイトークン・DB パスワード等）はリポジトリのコードに含めず、シークレット管理機構で保管しなければならない
- **FR-009**: 同一環境への反映は直列化され、並行実行によって古いコミットが新しいコミットを上書きしない
- **FR-010**: 各反映の成否・対象コミット・実行者が GitHub 上で追跡できなければならない
- **FR-011**: 反映失敗時は該当ジョブのみ再実行でき、再実行が安全（冪等）でなければならない
- **FR-012**: README に、デプロイの全体像（ブランチ ↔ 環境の対応・反映の流れ図）を記載しなければならない
- **FR-013**: README に、必要なすべてのシークレット・環境変数の「名前 / 用途 / 取得元 / 設定場所」の一覧表を記載しなければならない
- **FR-014**: README に、初期セットアップ手順（外部サービス側の準備を含む）とトラブルシューティング（再実行・手動デプロイ）を記載しなければならない
- **FR-015**: アプリの実行環境（stg / prod）ごとに異なる環境変数（DB 接続先・決済キー等）が正しく分離され、stg が prod のデータ・決済に接続してはならない

### Key Entities

- **環境（stg / prod）**: ブランチ（develop / main）に 1:1 対応する反映先の組。アプリ 2 つ + DB 1 つで構成される
- **デプロイ実行**: 1 回のマージに対応するパイプラインの実行単位。対象コミット・結果・実行ログを持つ
- **資格情報（シークレット）**: 外部サービスへの反映に必要なトークン・パスワード類。環境ごとに分離して保管される

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: stg デプロイの手動実行から反映完了まで 15 分以内（2026-07-17 改定。旧: マージから手作業ゼロで反映）
- **SC-002**: main へのマージから prod 反映完了まで、承認操作 1 回以外の手作業ゼロ
- **SC-003**: リポジトリ内（コード・履歴・設定ファイル）に平文の資格情報が 0 件
- **SC-004**: マイグレーション失敗時に「新アプリ + 旧スキーマ」の不整合状態が発生した回数 0 件
- **SC-005**: 新規メンバーが README のみを参照して、シークレット設定の準備（値の取得元の特定まで）を 1 時間以内に完了できる
- **SC-006**: stg 環境の動作確認で発見された問題が prod 反映前にブロックできる（stg を経由しない prod 反映が 0 件）

## Assumptions

- ブランチ運用は現状どおり: 機能ブランチ → `develop`（stg）→ `main`（prod）。hotfix も同じ経路を通す（main への直接マージはリリース PR のみ）
- 既存 CI（005 / ci.yml・full-test.yml）は継続し、本機能はデプロイ（CD）を追加する。デプロイの前提条件として既存のテスト群を利用する
- Vercel・Supabase の有料/無料プランの選定や課金はスコープ外（必要なプラン制約があれば plan 工程で明記する）
- ローカル開発環境（supabase start / make front-dev）は本機能の影響を受けない
- Stripe は環境ごとにテストモード（stg）と本番モード（prod）のキーを使い分ける。Stripe 側の webhook エンドポイント登録（stg / prod の URL）は初期セットアップ手順に含める
- デプロイの通知（Slack 等）は初期スコープ外。GitHub の標準通知で足りる
- ロールバックは「前のコミットの再デプロイ（アプリ）+ 逆方向マイグレーション（DB）」の手動運用とし、自動ロールバックは作らない
