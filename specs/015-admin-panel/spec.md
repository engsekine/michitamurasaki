# Feature Specification: 運営管理画面（admin-front）

**Feature Branch**: `015-admin-panel`

**Created**: 2026-06-19

**Status**: Draft

**Input**: User description: "管理画面をadmin-frontに作成したい　別でポートを立てるが、supabaseのDBはいじれるようにする　wordpressの管理画面のようなUIにしたい"

## 概要

ダイビングログサービスの運営担当者が、利用者向けアプリ（service-front）とは別に立ち上がる**専用の管理画面（admin-front）**にログインし、サービスのデータ（ユーザー・ダイブログ・マスタ類など）を一覧・検索・編集・削除できるようにする。UI は WordPress 管理画面のように「左サイドバーのメニュー → 一覧（テーブル）→ 詳細・編集フォーム」という運営者が直感的に操作できる体裁とする。一般利用者はこの画面にアクセスできない。

## Clarifications

### Session 2026-06-20

- Q: 同時編集の競合（複数管理者が同一レコードを更新）の扱いは？ → A: 楽観ロックで競合を検知し保存をブロック、再読み込みを促す（後勝ち上書きを防ぐ）
- Q: 他データから参照されているマスタ（例: ダイブサイト）の削除の動作は？ → A: 参照しているレコードがある間は削除をブロックし、参照件数を提示する
- Q: 管理者の権限階層は？ → A: 2段階（admin / superadmin）。通常管理者はデータ管理のみ、管理者の追加・無効化は superadmin のみ

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理者としてログインし管理画面に入る (Priority: P1)

運営担当者として、利用者向けアプリとは別の URL / ポートで提供される管理画面にログインし、サービス全体のデータを俯瞰できるダッシュボードに到達したい。一般利用者や未認証者はこの画面に一切入れないことが保証されていてほしい。

**Why this priority**: 管理者の認証とアクセス制御が成立しなければ、データ管理・モデレーションなど他のすべての運営機能が成立しない。かつ、利用者データを扱うため最初に閉じておくべきセキュリティ境界である。

**Independent Test**: 管理者権限を持つアカウントで管理画面にログインしダッシュボードに到達できること、権限を持たないアカウント・未認証アクセスは管理画面のいずれの URL でも拒否（ログイン誘導／アクセス不可表示）されることを、それぞれ単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 管理者権限を持つ運営担当者、**When** 管理画面のログイン情報を正しく入力する、**Then** ダッシュボード（運営者向けトップ）に遷移する
2. **Given** 管理者権限を持たない一般利用者、**When** 管理画面の URL に直接アクセスする、**Then** システムは管理画面の内容を表示せずアクセスを拒否する
3. **Given** 未認証の訪問者、**When** 管理画面の任意の URL にアクセスする、**Then** ログイン画面に誘導される
4. **Given** 管理画面にログイン済みの管理者、**When** ログアウトする、**Then** 以降は管理画面の各 URL にアクセスできなくなる

---

### User Story 2 - データを一覧・検索して詳細を確認する (Priority: P1)

運営担当者として、左サイドバーのメニューから管理対象（ユーザー、ダイブログ、ダイブサイト等）を選び、一覧テーブルで件数・主要項目を確認し、キーワードや条件で絞り込み、特定レコードの詳細を開いて内容を把握したい。

**Why this priority**: 「いじる（編集・削除）」の前提として、対象を正確に見つけて中身を確認できることが運営業務の基盤になる。閲覧だけでも問い合わせ対応・調査という価値を独立して提供できる。

**Independent Test**: 各管理対象のメニューから一覧を開き、ページングされた一覧の表示・キーワード検索・1 件の詳細表示までを、編集機能なしでも単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 管理画面にログイン済み、**When** サイドバーから「ユーザー」を選ぶ、**Then** 登録ユーザーの一覧が主要項目（識別名・登録日など）とともにページング表示される
2. **Given** 一覧表示中、**When** キーワードで検索する、**Then** 条件に一致するレコードのみが表示され、件数が分かる
3. **Given** 一覧表示中、**When** 1 件を選んで詳細を開く、**Then** そのレコードの全項目と関連データ（例: ユーザーに紐づくダイブログ件数）が表示される
4. **Given** 一覧が 0 件、**When** 該当データがない、**Then** 「データがありません」と明示され空テーブルでも崩れない

---

### User Story 3 - データを編集・作成・削除する (Priority: P1)

運営担当者として、詳細画面または専用フォームからレコードの内容を修正し、マスタ系データ（ダイブサイト等）を新規追加し、不要・不適切なレコードを削除（または非公開化）したい。誤操作を防ぐため、削除や重要変更には確認を挟みたい。

**Why this priority**: 「supabase の DB をいじれるようにする」という中心的な要求そのもの。データの修正・追加・削除ができて初めて管理画面の主目的が満たされる。

**Independent Test**: 管理対象 1 種（例: ダイブサイト）に対して、新規作成 → 一覧反映 → 編集 → 反映 → 削除 → 一覧から消える、の一連を単独で検証できる。

**Acceptance Scenarios**:

1. **Given** レコードの編集フォーム、**When** 項目を変更して保存する、**Then** 変更が永続化され、一覧・詳細に反映される
2. **Given** マスタ追加フォーム、**When** 必須項目を入力して作成する、**Then** 新規レコードが作成され一覧に現れる
3. **Given** 入力値が制約（必須・形式・文字数・参照整合性など）に違反、**When** 保存しようとする、**Then** システムは保存せずどの項目が不正かを明示する
4. **Given** レコードの削除操作、**When** 削除を実行する、**Then** 確認を経たうえで削除（または非公開化）され、取り消し不能な操作であることが事前に伝わる
5. **Given** 他データから参照されているレコードの削除、**When** 削除しようとする、**Then** 参照しているレコードがある間は削除がブロックされ、参照件数が提示される

---

### User Story 4 - 運営状況をダッシュボードで把握する (Priority: P2)

運営担当者として、ログイン後のトップで登録ユーザー数・ダイブログ記録数・直近の増加傾向などの全体 KPI を一目で把握し、各管理メニューへ素早く移動したい。

**Why this priority**: 日々の運営判断に有用だが、認証・一覧・編集が揃った後の付加価値であり MVP の必須ではない。

**Independent Test**: ダッシュボードに主要 KPI が数値で表示され、各カードから対応する一覧へ遷移できることを単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 管理画面にログイン済み、**When** ダッシュボードを開く、**Then** 登録ユーザー数・ダイブログ総数など主要指標が数値で表示される
2. **Given** ダッシュボードの指標カード、**When** カードを選ぶ、**Then** 対応する管理対象の一覧に遷移する

---

### User Story 5 - 操作履歴を追える (Priority: P3)

運営担当者・責任者として、誰がいつどのレコードに対して編集・削除を行ったかを後から確認し、誤操作や不正の調査に使いたい。

**Why this priority**: 利用者データを書き換えられる管理画面では監査性が重要だが、初期リリースは限られた信頼できる運営者のみが使う前提のため P3 とする。

**Independent Test**: 任意の編集・削除を行った後、操作ログに「実行者・対象・操作種別・日時」が記録され、一覧で確認できることを単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 管理者がレコードを編集・削除した、**When** 操作ログを開く、**Then** 実行者・対象・操作種別・日時が時系列で確認できる

---

### Edge Cases

- 管理者が編集中に別の管理者が同じレコードを更新した場合（同時編集の競合）は、楽観ロックで検知して保存をブロックし、再読み込みを促す（FR-022）
- 削除・重要変更が利用者向けアプリ（service-front）の表示に即時に影響する場合の周知・反映タイミング
- 他テーブルから参照されているマスタ（例: ダイブサイト）を削除しようとした場合は、参照がある間は削除をブロックし参照件数を提示する（FR-014）
- 大量データ（数万件規模）の一覧表示・検索でも応答が破綻しないこと
- 管理者自身のアカウントや他の管理者アカウントを誤って無効化・削除しないための保護
- セッション期限切れ後に編集を保存しようとした場合の挙動（再ログイン誘導・入力内容の喪失防止）
- 利用者の個人情報（プロフィール等）を扱う画面での過剰な情報露出の抑制

## Requirements *(mandatory)*

### Functional Requirements

#### アクセス制御・認証

- **FR-001**: システムは管理画面を、利用者向けアプリ（service-front）とは独立して提供し、一般利用者向けの導線からは到達できないようにしなければならない
- **FR-002**: システムは管理者権限を持つ利用者のみ管理画面にアクセスを許可し、権限を持たない認証済み利用者および未認証アクセスはすべて拒否しなければならない
- **FR-003**: システムは権限チェックを画面（ルーティング）層だけでなく**データ操作層（クエリ・更新・削除）にも多層で適用**し、URL 直打ち・API 直叩き等の経路でも未権限者にデータを露出してはならない
- **FR-004**: 管理者は管理画面からログイン・ログアウトでき、ログアウト後は管理画面の各 URL にアクセスできなくなければならない
- **FR-005**: システムは管理者を、利用者アカウントとは分離した専用の管理者アカウント体系で識別しなければならない。管理画面のセッションは利用者向けアプリのセッションと分離し、利用者アカウントが管理画面のセッションを獲得できないようにする。管理者は **2 段階の権限（通常管理者 / 上位管理者）** を持ち、通常管理者はデータ管理のみ、管理者アカウントの追加・無効化は上位管理者のみが行える

#### データ管理（一覧・検索・詳細）

- **FR-006**: システムはサイドバーのメニューから管理対象を選択でき、選択した対象のレコード一覧をページング付きで表示しなければならない
- **FR-007**: システムは一覧でキーワード検索および主要項目での絞り込み・並び替えを提供しなければならない
- **FR-008**: システムは各レコードの詳細を表示し、関連データ（例: ユーザーに紐づくダイブログ）の概要を把握できるようにしなければならない
- **FR-009**: システムは一覧が 0 件の場合でも、空であることを明示しレイアウトを崩してはならない

#### データ管理（作成・編集・削除）

- **FR-010**: 管理者はレコードの内容を編集して永続化でき、変更は一覧・詳細に反映されなければならない
- **FR-011**: 管理者はマスタ系データ（ダイブサイト等）を新規作成できなければならない
- **FR-012**: システムは保存時に入力値の制約（必須・形式・文字数・選択肢・参照整合性など）を検証し、違反時は保存せずどの項目が不正かを明示しなければならない
- **FR-013**: 管理者はレコードを削除（または非公開化）でき、取り消し不能な操作の前には確認を挟まなければならない
- **FR-014**: システムは他データから参照されているレコードの削除に対し、参照しているレコードが存在する間は削除をブロックし、参照件数を提示しなければならない（連鎖削除や参照解除による利用者データの巻き込みを行わない）
- **FR-015**: システムは管理者アカウントの追加・無効化を上位管理者のみに許可し、自分自身の無効化、および最後の上位管理者の無効化をブロックして、管理権限の喪失や誤操作を防がなければならない。role の昇格/降格も DB トリガ（prevent_last_superadmin_removal）が最後の superadmin の降格を防ぐ。物理 DELETE も同トリガ群で保護
- **FR-016**: 管理画面で行ったデータ変更は、利用者向けアプリ（service-front）が参照する同一データに正しく反映されなければならない
- **FR-017**: システムは主要なドメインエンティティ（ユーザー・ダイブログ・ダイブサイト等）には用途特化した管理画面を提供し、それ以外のデータには汎用テーブルエディタを提供する（特化画面と汎用画面の併用）。汎用テーブルエディタは閲覧 + 行削除（削除可否はテーブルごとの許可設定に従う）。行編集は未実装（MVP スコープ外）。汎用画面で扱える対象・項目は許可リストで限定し、認証基盤や内部用の情報を露出してはならない
- **FR-018**: システムは破壊的操作について、原則としてソフトデリート（論理削除）または非公開化を用いなければならない。物理削除は限定的な場合にのみ確認を経て許可する。物理削除を実行できるのは admin 以上（現実装）。user_details の物理削除は不可（table-editor で deletable: false）。また、管理画面で行われた全データ変更について操作ログ（実行者・対象・操作種別・日時）の記録を必須とし、操作ログ自体は改変・削除できないようにする
- **FR-022**: システムは同一レコードの同時編集に対し楽観ロックで競合を検知しなければならない。保存時点で対象が他者により更新されていた場合は保存をブロックし、最新内容の再読み込みを促す（無警告の後勝ち上書きをしてはならない）

#### UI / 操作性

- **FR-019**: システムは WordPress 管理画面に準じた構成（左サイドバーのナビゲーション、メイン領域の一覧テーブルと編集フォーム、上部のヘッダー）を提供し、運営者が学習コストなく操作できるようにしなければならない
- **FR-020**: システムは操作結果（保存成功・作成成功・削除完了・エラー）を明確なフィードバックとして利用者に伝えなければならない
- **FR-021**: 管理画面はキーボード操作・スクリーンリーダー・カラーコントラストなどアクセシビリティ基準（WCAG 2.1 AA）を満たさなければならない

### Key Entities *(include if feature involves data)*

管理画面が扱う既存データ（Supabase の `public` スキーマ）。

- **ユーザー（users / user_details）**: サービス利用者のアカウントとプロフィール（姓名・ニックネーム・生年月日・性別など）。管理対象の中心。
- **ダイブログ（dives）**: 利用者が記録した 1 本ごとの潜水ログ。ユーザーに紐づく取引系データ。
- **ダイブサイト（dive_sites）**: ポイント名などのマスタ。利用者のダイブログから参照される。
- **写真（dive_photos）**: ダイブログに添付された写真。モデレーション対象になりうる。
- **資格（certifications / certification_tags）**: 利用者の取得資格情報。
- **ダイブプラン（dive_plans / plan_packing_items）**: 利用者のダイブ計画と持ち物。
- **レギュレータ等の装備（regulators）**: 利用者の装備マスタ/記録。
- **管理者**: 管理画面にアクセスできる運営担当者。利用者とは分離した専用の管理者アカウント体系で識別し、2 段階の権限（通常管理者 / 上位管理者）を持つ（FR-005）。
- **操作ログ**: 管理画面で行われた全データ変更の記録（実行者・対象・操作種別・日時）。記録は必須で、ログ自体は改変・削除不可（FR-018）。一覧での参照は US5（P3）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 権限を持たない利用者・未認証アクセスが管理画面のデータに到達できる経路が 0 件である（全ページ・全操作で権限チェックが効いている）
- **SC-002**: 運営担当者は、対象データを「メニュー選択 → 検索 → 該当レコードを開く」まで 30 秒以内に到達できる
- **SC-003**: 運営担当者は、レコードの編集・マスタの新規作成・削除のそれぞれを、マニュアルなしで初回から完了できる（主要タスクの初回完了率 90% 以上）
- **SC-004**: 一覧・検索の操作結果が、数万件規模のデータでも体感的な待ちなく（おおむね 2 秒以内に）表示される
- **SC-005**: 管理画面での変更が利用者向けアプリの表示に正しく反映され、データ不整合に起因する不具合が 0 件である
- **SC-006**: 削除・重要変更の前に確認が表示され、確認なしに取り消し不能な操作が実行されることがない

## Assumptions

- 管理画面は service-front とは別アプリ（別ポート / 別 URL）として `admin-front` で提供し、データソースは service-front と**同一の Supabase プロジェクト**を共有する（利用者データに対する運営操作が目的のため）。
- 管理画面の利用者は限られた信頼できる運営担当者であり、一般公開はしない。
- 管理対象は当面、既存の `public` スキーマのドメインデータ（上記 Key Entities）を主対象とする。認証基盤（`auth` スキーマ）そのものの管理は本仕様の主目的としない。
- 既存のデータ制約（必須・文字数・参照整合性・RLS など）は管理画面からの操作でも尊重する。RLS を回避する強い権限が必要な場合は、その境界を plan で明示する（Constitution IV: Security & RLS by Default）。
- UI・実装は既存スタック（Next.js App Router / TypeScript / Tailwind / Supabase）と Feature-based アーキテクチャに準拠する（詳細は `/speckit-plan` で確定）。
- 「WordPress のような UI」は体裁・操作モデル（サイドバー＋一覧＋編集フォーム）の参照であり、WordPress そのものや特定 CMS の採用を意味しない。
- 多言語対応・テーマ切替・プラグイン機構などの CMS 的拡張は本仕様の対象外。

## 補足: リポジトリ構成（解決済み）

本スペック作成時点で懸念とされた「`service-front` が `admin-front` に改名された状態」は解消済み（`service-front` は無傷、作業ツリーはクリーン）。構成方針は確定済み：利用者向けアプリ（`service-front`）を残したまま、管理画面を**別アプリ `admin-front`** としてモノレポに追加する（ルート `package.json` の `workspaces` に登録済み）。詳細は `plan.md` を参照。
