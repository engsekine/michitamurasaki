# Quickstart: ログのいいね機能 手動検証

**Feature**: 027-log-likes | **Plan**: [plan.md](./plan.md)

トリガー・RLS はユニットテストで担保できないため、ここでの手動検証を必須とする（025 と同方式）。

## 前提

```bash
# ローカル Supabase 起動 + マイグレーション + シード（テストユーザー A / B が作成される）
# 注意: config.toml が SMTP_ENABLED を参照するため root .env に SMTP_ENABLED=false を定義しておく
make supabase-reset

# service-front 起動
npm run dev --workspace service-front
```

- ユーザー A: 公開ログを 1 件以上持つ（seed またはログ作成 → 公開設定 ON）
- ユーザー B: A をフォローしている（タイムラインに A のログが出る状態）

## シナリオ 1: いいねの付け外し（US1 / FR-001〜006・013）

1. B でログイン → ホームのタイムラインで A の公開ログのいいねボタンを押す
   - **期待**: 件数が即座に +1、ボタンが「いいね済み」表示に変わる（1 秒以内 / SC-001）
2. 同じボタンをもう一度押す
   - **期待**: 件数が -1、未いいね表示に戻る
3. A の公開ログ詳細（`/dives/[id]`）を開いていいねする
   - **期待**: 詳細でも同じ操作ができ、タイムラインに戻ると状態が一致している
4. B が自分自身のログ詳細を開く
   - **期待**: いいねボタンは表示されない。件数のみ表示（US1-AC5）
5. （DB 層防御の確認）psql で B として自分のログへ INSERT を試みる:
   ```sql
   -- ローカル DB: 42501 (RLS 違反) になることを確認
   set role authenticated;
   set request.jwt.claims = '{"sub":"<BのユーザーID>","role":"authenticated"}';
   insert into dive_likes (user_id, dive_id) values ('<BのID>', '<Bの自分のログID>');
   ```
6. 連打テスト: いいねボタンを素早く複数回押す
   - **期待**: 件数が 1 しか増えない / エラー画面にならない（FR-003・冪等変換）

## シナリオ 2: いいね一覧（US2 / FR-007〜009）

1. B で複数の公開ログ（A のログ 3 件）にいいねする
2. ホーム上部のタブ「いいねしたログ」を選択
   - **期待**: `/likes` に遷移し、いいねした 3 件が新しい順に表示される（US2-AC1）
3. ヘッダーのナビ「いいね」からも開く
   - **期待**: 同じ一覧が表示される（導線 2 箇所 / FR-008a）
4. 一覧の項目を選択
   - **期待**: ログ詳細へ遷移（US2-AC2）。詳細でいいねを取り消して `/likes` に戻る → その項目が消えている（US2-AC3）
5. A が対象ログを非公開化（または削除）する → B が `/likes` を再表示
   - **期待**: そのログは一覧から消える。エラーにならない（US2-AC5 / FR-009）
6. いいねを全て取り消して `/likes` を開く
   - **期待**: 「いいねしたログはありません」の空状態（US2-AC4）
7. 21 件以上いいねした状態で `/likes` を開く
   - **期待**: 20 件 + 「さらに読み込む」でページング（SC-005）

## シナリオ 3: いいね通知（US3 / FR-010〜012）

1. B が A の公開ログにいいねする → A でログイン
   - **期待**: ヘッダーの未読バッジ +1。通知一覧に「B さんがあなたのログにいいねしました」（US3-AC1）
2. A が通知をタップ
   - **期待**: 該当ログ詳細へ遷移し、その通知が既読になる（US3-AC2）
3. B がいいね取り消し → 再いいねを 3 回繰り返す → A が通知一覧を開く
   - **期待**: B からの通知は 1 件のまま（集約）。手順 2 で既読にした場合、未読には戻らない（US3-AC3 / FR-011）
4. 別ユーザー C も同じログにいいねする
   - **期待**: B と C の通知が別々に表示される（US3-AC5）
5. A が通知設定で「ログにいいねされたとき」を OFF → B が別のログにいいねする
   - **期待**: 通知は増えない。ただし件数には反映される（US3-AC4 / FR-012）
6. （SQL で確認）集約 upsert の実データ:
   ```sql
   select recipient_id, type, actor_id, resource_id, occurred_at, read_at
   from notifications where type = 'log_liked';
   -- 同一 (actor_id, resource_id) が 1 行であること、read_at が維持されていることを確認
   ```

## 自動テスト・静的チェック

```bash
npm run test --workspace service-front       # Vitest（actions / queries / lib / コンポーネント）
npm run check --workspace service-front      # biome
npx tsc --noEmit -p service-front            # 型チェック
SMTP_ENABLED=false npx supabase db lint      # マイグレーションの lint（CI の db-lint と同等）
```

## 完了条件との対応

| Success Criteria | 検証手順 |
|------------------|----------|
| SC-001（1 操作・1 秒以内） | シナリオ 1-1 |
| SC-002（2 操作以内で到達） | シナリオ 2-2〜4（タブ → 項目選択） |
| SC-003（通知で気づける） | シナリオ 3-1〜2 |
| SC-004（通知は最新 1 件） | シナリオ 3-3 |
| SC-005（100 件超でも劣化しない） | シナリオ 2-7（ページング動作） |
