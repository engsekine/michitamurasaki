# Feature Specification: ユーザー ID とプロフィール URL

**Feature Branch**: `worktree-034-nickname-profile-url`（Rev.1 時の名称。spec ディレクトリは `034-profile-user-id`）

**Created**: 2026-07-12

**Status**: Draft（Rev.2 — ニックネーム方式からユーザー ID 方式へ全面改訂）

**Input**: User description: "マイプロフィールのidをニックネームにしたい（Rev.1）→ ユーザー情報入力の時に、ユーザーIDを設定して英語のみでユーザープロフィールのIDにしたい（Rev.2）"

## Clarifications

### Session 2026-07-12

- Q: プロフィール URL の識別子は？ → A: **Rev.2 で方針転換**。ニックネーム（日本語可・表示名）ではなく、ユーザーが設定する英語のみの「ユーザー ID」を URL 識別子にする。ニックネームは表示名としてそのまま残す（表示名とユーザー ID の分離）
- Q: ユーザー ID の必須性は？ → A: **必須**。未リリースのため移行の複雑さを避け、新規登録では必須入力、既存ユーザー（開発環境のみ）はマイグレーションで自動採番して埋める（あとから変更可能）
- Q: 旧ニックネーム URL（Rev.1 実装）の互換は？ → A: 不要。Rev.1 は未リリースのため、ニックネームでの URL 解決は廃止してよい。内部 ID（uuid）形式 URL の転送は引き続き維持する

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ユーザー ID を設定してプロフィール URL になる (Priority: P1)

ユーザーは会員情報の入力時（新規登録・Google ログイン初回のプロフィール補完）に、英語のみのユーザー ID（例: `taro-diver`）を必須で設定する。プロフィールページ（自分・他人とも）の URL はこのユーザー ID で表される（例: `/users/taro-diver`）。アプリ内のプロフィールへの導線（ヘッダー・タイムライン・フォロー/フォロワー一覧・バディ表示・通知など）もすべてユーザー ID の URL になる。ニックネームは従来どおり表示名として使われる。

**Why this priority**: この機能の主目的。英字のみの ID なので URL が常にそのまま読め、共有しやすい。

**Independent Test**: 新規ユーザーがユーザー ID を設定して登録し、プロフィール URL・各導線がその ID になることを確認すれば単体でテスト可能。

**Acceptance Scenarios**:

1. **Given** 新規登録フォーム, **When** ユーザー ID を含む必須項目を入力して登録する, **Then** プロフィール URL が `/users/<ユーザー ID>` になる
2. **Given** ユーザー ID 欄を空のまま, **When** 登録する, **Then** エラーが表示され登録できない（必須）
3. **Given** ログイン済みユーザー, **When** ヘッダーからマイプロフィールを開く, **Then** URL のユーザー識別部分が自分のユーザー ID になっている
4. **Given** タイムライン・フォロー一覧・バディ表示など他ユーザーへの導線, **When** ユーザーを選択する, **Then** ユーザー ID の URL のプロフィールページに遷移する（表示される名前はニックネームのまま）
5. **Given** フォロワー・フォロー中の一覧ページ, **When** 開く, **Then** これらの URL もユーザー ID 基準になっている
6. **Given** 存在しないユーザー ID の URL, **When** アクセスする, **Then** 「ページが見つかりません」が表示される
7. **Given** 大文字を含む URL（例: `/users/TARO-DIVER`）, **When** アクセスする, **Then** 同一ユーザーに解決される（ユーザー ID は小文字で保存され、照合は大文字小文字を区別しない）

---

### User Story 2 - ユーザー ID の形式と一意性 (Priority: P1)

ユーザー ID は「小文字英字・数字・ハイフン・アンダースコアのみ、3〜30 文字、先頭は英字」で、全ユーザーで一意。大文字を入力した場合は小文字として扱う。既に使われている ID・予約されたパス名（ユーザー検索など）は登録できない。

**Why this priority**: URL 識別子としての成立条件そのもの。US1 と同時に満たす必要がある。

**Independent Test**: 登録・変更フォームで不正な形式（日本語・記号・短すぎ/長すぎ・先頭数字）・重複 ID・予約語を入力して、すべて拒否されることを確認すれば単体でテスト可能。

**Acceptance Scenarios**:

1. **Given** 登録・変更フォーム, **When** 日本語・スペース・許可外の記号を含む ID を入力する, **Then** 形式エラーが表示される
2. **Given** 登録・変更フォーム, **When** 2 文字以下・31 文字以上・数字始まりの ID を入力する, **Then** 形式エラーが表示される
3. **Given** 他のユーザーが使用中の ID, **When** 登録・変更する, **Then** 「既に使われています」エラーになる（大文字小文字だけ変えても不可）
4. **Given** 予約パス名（ユーザー検索など）と同名の ID, **When** 登録・変更する, **Then** 拒否される
5. **Given** 大文字混じりの入力（例: `TaroDiver`）, **When** 登録する, **Then** 小文字（`tarodiver`）として保存・表示される

---

### User Story 3 - ユーザー ID の変更と旧 URL の扱い (Priority: P2)

ユーザーは会員情報からユーザー ID を変更できる。変更するとプロフィール URL も即時切り替わり、変更前の ID の URL は無効になる（その ID は他のユーザーが取得できる）。内部 ID（uuid）形式の URL は引き続き現在のユーザー ID の URL へ転送されるため、uuid 経由の参照（通知など）は変更に影響されない。

**Why this priority**: 変更可能である以上避けられない挙動の定義。US1/US2 の成立後に検証すればよい。

**Independent Test**: ユーザー ID を変更し、新 URL で表示・旧 URL が 404・uuid URL が新 URL へ転送されることを確認すれば単体でテスト可能。

**Acceptance Scenarios**:

1. **Given** ユーザー ID を変更したユーザー, **When** マイプロフィールを開く, **Then** URL が新しいユーザー ID になっている
2. **Given** 変更前のユーザー ID の URL, **When** アクセスする, **Then** 「ページが見つかりません」（誰もその ID を使っていない場合）
3. **Given** uuid 形式の URL, **When** アクセスする, **Then** 変更後のユーザー ID の URL へ転送される

---

### Edge Cases

- uuid 形式とユーザー ID の判別 → ユーザー ID は最大 30 文字・uuid は 36 文字のため形式上衝突しない。uuid 形式の URL は uuid として解釈し、現在のユーザー ID の URL へ転送する
- 予約パス名（`search`）と同名のユーザー ID → 登録時に拒否する（大文字小文字問わず）
- 既存ユーザー（開発環境）のユーザー ID → マイグレーションで一意な初期値を自動採番する（例: `user-` + 内部 ID 先頭 8 桁）。ユーザーは会員情報からいつでも変更できる
- ユーザー ID 変更直後に開きっぱなしの画面から旧 ID へ遷移した場合 → 「ページが見つかりません」（uuid 形式の導線は影響なし）
- 大文字だけが異なる URL（`/users/Taro` と `/users/taro`）→ 同一ユーザーに解決される

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムはユーザーごとに一意の「ユーザー ID」を保持し、プロフィールページ・フォロワー一覧・フォロー中一覧の URL の識別子として使用しなければならない
- **FR-002**: ユーザー ID の形式は「小文字英字・数字・ハイフン・アンダースコア、3〜30 文字、先頭は英字」とし、入力の大文字は小文字に正規化して保存しなければならない
- **FR-003**: ユーザー ID は新規登録（メール・Google 補完とも）の必須入力項目でなければならない。重複・形式不正・予約パス名は登録時に拒否する
- **FR-004**: アプリ内のプロフィールへのすべての導線（マイプロフィール・タイムライン・フォロー/フォロワー一覧・バディ表示・いいね・通知・ユーザー検索結果など）はユーザー ID の URL を生成しなければならない。表示する名前はニックネームのまま変えない
- **FR-005**: システムは内部 ID（uuid）形式の URL へのアクセスを、現在のユーザー ID の URL へ転送しなければならない（フォロワー・フォロー中の下層 URL も同様）
- **FR-006**: ユーザーは会員情報からユーザー ID を変更でき、変更は URL に即時反映されなければならない。変更前の ID の URL は無効となり、その ID は他ユーザーが取得できる
- **FR-007**: システムは存在しないユーザー ID・uuid の URL に対して「ページが見つかりません」を表示しなければならない
- **FR-008**: 既存ユーザー（未設定）にはデータ移行時に一意な初期ユーザー ID を自動採番しなければならない（全ユーザーが必ずユーザー ID を持つ状態にする）
- **FR-009**: プロフィールの閲覧可否・表示内容は現行と同一でなければならない（URL 形式の変更によってアクセス制御・表示範囲を変えない）
- **FR-010**: ニックネームは表示名として従来どおり機能し、本機能による制約変更・URL への使用は行わない

### Key Entities

- **ユーザー ID**: ユーザーが設定する英語のみの一意な識別子（3〜30 文字・小文字英数字と `-` `_`・先頭英字）。URL の一部として公開される。変更可能
- **ニックネーム**: 既存の表示名。本機能では役割を変えない（URL には使わない）
- **ユーザープロフィール**: 既存機能。URL 上の識別子が uuid からユーザー ID に変わる

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: すべてのユーザーがユーザー ID を持ち（未設定ユーザー 0 件）、プロフィール URL を見ただけで誰のページか判別できる
- **SC-002**: アプリ内のプロフィール導線の 100% がユーザー ID の URL を生成する
- **SC-003**: uuid 形式の URL の 100% が現在のユーザー ID の URL へ転送され、リンク切れにならない
- **SC-004**: ユーザー ID 変更後、5 秒以内に新しい URL でプロフィールに到達できる
- **SC-005**: 新規登録でユーザー ID の入力に起因するエラーの手戻りが 1 画面内で完結する（形式・重複エラーがその場で表示される）

## Assumptions

- **未リリース前提**: Rev.1（ニックネーム URL）の互換は持たない。uuid URL の転送のみ維持する
- **既存ユーザーの初期値**: 自動採番（`user-` + 内部 ID 先頭 8 桁など衝突しない規則）とし、変更を促す通知等は行わない（開発環境のみのため）
- **ユーザー ID の変更ポリシー**: 旧 ID の予約・転送はしない（一般的な SNS のユーザー名変更と同じ割り切り）
- **予約パス名**: `search`（ユーザー検索）を予約語とし、今後 `/users/` 配下にページを増やす場合は予約語リストに追加する
- **ニックネームの一意制約**: 既存のまま維持する（検索・表示の重複防止という導入時の目的は変わらないため）
- 対象はユーザー向けアプリのみ（管理画面は対象外）
