ブランチの変更内容をサブエージェントで並列チェックし、人間のレビューを支援するレポートを生成する。

## 入力パターン

- `/review` - 現在のブランチのベースブランチとの差分をレビュー
- `/review <NNN>-<feature>` - 指定 feature（例: `002-dive-log-crud`）の仕様スコープに沿ってレビュー（`specs/<NNN>-<feature>/` の spec.md / tasks.md の受け入れ条件も参照）

## 前提確認

- 変更差分（未ステージ / ステージング済み / コミット済みのいずれか）が存在すること（なければ「レビュー対象がありません」と伝えて終了）

## 手順

### 1. 変更内容の収集（内部処理）

[.claude/rules/diff-scope.md](../../rules/diff-scope.md) に従い、ベースブランチを検出したうえで**未ステージ・ステージング済み・コミット済みの 3 層**を統合した差分を収集する。コミット一覧は `git log <ベース>..HEAD --oneline` で取得する。

上記を統合して「レビュー対象の全差分」「変更ファイルリスト」を構成する。

feature ID が指定されている場合は `specs/<NNN>-<feature>/spec.md`（受け入れシナリオ・FR）と `tasks.md`（タスクのスコープ・完了条件）を読み、レビュー観点に含める。

**出力**: ベースブランチ名、変更ファイルリスト、差分詳細、コミット一覧 → 手順2〜3の入力

### 2. レビュールールの収集（内部処理）

以下のファイルを探索し、存在するものをすべてレビュー基準として読み込む。

| ファイル | 内容 |
| --- | --- |
| `.coderabbit.yaml` | CodeRabbitのレビュールール |
| `.claude/CLAUDE.md` | プロジェクトのコードスタイル・規約 |
| `.claude/rules/*.md` | 言語別コーディング規約 |
| `eslint.config.*` / `.eslintrc.*` | ESLint設定（ルートのみ） |
| `tsconfig.json` | TypeScript設定 |
| `specs/<NNN>-<feature>/spec.md` | 該当する機能仕様（spec-kit 形式） |
| `specs/<NNN>-<feature>/plan.md` | 該当する実装計画 |
| `specs/<NNN>-<feature>/screens/` | 該当する画面仕様 |
| `specs/<NNN>-<feature>/data-model.md` | 該当するテーブル仕様 |

**出力**: レビュー基準の集合 → 手順3のチェック観点

### 3. サブエージェントによる並列レビュー

以下の**4つ**のサブエージェントを `Agent` ツールで**1 メッセージ内で並列に**起動する。各エージェントには変更ファイルリストと差分詳細を渡す。

**1. code-reviewer**（コード品質チェック）

渡すプロンプト:
```
以下の変更ファイルをレビューしてください。
変更ファイル: [変更ファイル一覧]
差分詳細: [差分の内容]

チェック観点: 型安全性、エラーハンドリング、命名規則、コード規約違反、セキュリティ脆弱性、パフォーマンス問題
報告形式: 各指摘を Error / Warning / Info に分類し、ファイル:行番号と説明を返す
```

**2. doc-checker**（設計書・仕様書との整合性チェック）

渡すプロンプト:
```
以下の変更ファイルと設計書・仕様書を比較してください。
変更ファイル: [変更ファイル一覧]
設計書: [該当する設計書パス]（存在しない場合は「設計書なし」と報告）
仕様書: [該当する仕様書パス]（存在しない場合は「仕様書なし」と報告）

報告形式: 整合 / 差異あり（差異の内容）で返す
```

設計書・仕様書の特定方法: `specs/<NNN>-<feature>/`（spec.md / plan.md / data-model.md / screens/）配下のファイル名・見出しを確認し、変更ファイルの機能領域・画面・テーブルと一致するものを渡す（設計書としては plan.md を渡す）。該当なしの場合は「なし」と指定する。

**3. impact-analyzer**（変更影響の分析）

渡すプロンプト:
```
以下の変更が他のファイルや機能に与える影響を分析してください。
変更ファイル: [変更ファイル一覧]

分析観点: 変更ファイルを import しているファイル、型の変更による影響、APIの互換性
報告形式: 影響を受けるファイル・機能のリストを返す。影響なしの場合は「影響なし」
```

**4. diff-checker（general-purpose エージェント）**（テキスト品質・影響範囲の一括チェック）

上記 1〜3 のエージェントと同じメッセージ内で `general-purpose` エージェントを起動し、以下の 5 チェックを委譲する（メインループで自前実行しない。コンテキスト消費を抑えるため）。

**判定基準（全チェック共通）:**

| レベル | 基準 |
|--------|------|
| **Error** | バグの原因になる問題、セキュリティ脆弱性、ビルド・型エラー |
| **Warning** | 規約違反、保守性の低下、パフォーマンス懸念 |
| **Info** | スタイル改善の提案、参考情報 |

渡すプロンプト（変更ファイルリスト・差分詳細・ベースブランチ名を添える）:
```
以下の変更差分に対して 5 つのチェックを実行し、指摘を Error / Warning / Info に分類して
ファイル:行番号付きで返してください。

1. タイポチェック — .claude/skills/check-typo/SKILL.md の「スペルチェック」以降の手順に従う
2. 表記ゆれチェック — 差分の追加行から以下のパターンを検出:
   - 日本語: ユーザー vs ユーザ / サーバー vs サーバ / データベース vs DB
   - 英語: color vs colour / center vs centre
   - 記号: 〜 vs ～ / ー vs −
   - 単位: 10px vs 10 px
   - プロジェクト全体で Grep し、多数派への統一を推奨する（Info として報告）
3. 影響URLチェック — .claude/skills/check-diff-impact/SKILL.md の「影響URLの特定」節に従う
4. 共通化チェック — 変更差分と変更ファイル全体を解析:
   - 高（Warning）: 完全同一コードが3箇所以上 / ビジネスロジックの重複
   - 中（Info）: 類似コードが2箇所以上 / 設定値の散在
   - 低（Info）: パターンは似ているが文脈が異なる
5. 不要なexportチェック — 差分の export 宣言を抽出し、プロジェクト内の import を Grep で検索:
   - 参照なし → Warning として報告
   - 除外: export default、index.ts の再エクスポート、package.json の exports 対象
   - import 逆引きは .claude/rules/diff-scope.md の「import 逆引きの方法」に従う

報告形式: チェックごとに見出しを分け、指摘 0 件のチェックは「なし」と返す
```

### 4. レビューレポートの統合

手順3の 4 エージェントの全結果を統合し、以下のフォーマットで報告する。各セクションが0件の場合は「なし」と記載する。

```
コードレビューレポート

対象: <ベースブランチ>...<ブランチ名> (<コミット数>コミット, <変更ファイル数>ファイル)
feature: <NNN>-<feature>（該当する場合。なければ省略）

─────────────────────────
Error（修正必須）
─────────────────────────
- [ファイル:行番号] [説明]

─────────────────────────
Warning（修正推奨）
─────────────────────────
- [ファイル:行番号] [説明]

─────────────────────────
Info（参考情報）
─────────────────────────
- [ファイル:行番号] [説明]

─────────────────────────
ドキュメント整合性
─────────────────────────
- 設計書: [整合 / 差異あり（内容） / なし]
- 仕様書: [整合 / 差異あり（内容） / なし]

─────────────────────────
変更影響（ファイル・機能・URL）
─────────────────────────
- [影響を受けるファイル・機能]（or 影響なし）
- 影響URL: [service-front / admin-front 別のURL一覧]（or なし）

─────────────────────────
タイポ・表記ゆれ
─────────────────────────
- タイポ: [件数]件
- 表記ゆれ: [件数]件

─────────────────────────
共通化候補
─────────────────────────
- 高: [件数]件 / 中: [件数]件 / 低: [件数]件（or なし）

─────────────────────────
不要なexport
─────────────────────────
- [ファイル:行番号] `export [名前]` — 参照箇所なし（or なし）

─────────────────────────
総合判定: [LGTM / 要修正 / 要確認]
─────────────────────────
```

**総合判定の基準:**
- **LGTM**: Error が 0件
- **要修正**: Error が 1件以上
- **要確認**: Error は 0件だが Warning が 5件以上、またはドキュメント差異あり

### 5. 問題がある場合のアクション提案

Errorがある場合:
```
修正するには:
  /code-fix
```

## $ARGUMENTS

- `/review` - 現在のブランチの変更をレビュー
- `/review <NNN>-<feature>` - 指定 feature の仕様スコープに沿ってレビュー
